Two people edit the same thing at nearly the same moment on two different servers. Which change survives? A tempting answer is "whichever happened last, just check the timestamps." It sounds obviously correct. It's called last-write-wins, and it quietly loses people's data all the time, because of one fact that surprises almost everyone: computers do not agree on what time it is.

Start with the situation. In a distributed database, the same piece of data lives on multiple servers for availability. Normally writes are coordinated, but in systems that favor staying available during network trouble, two servers might each accept a write to the same key at nearly the same time, and only later compare notes. When they do, they find two different values and must decide which one to keep. Last-write-wins resolves it by attaching a timestamp to each write and keeping the one with the later timestamp. Simple, no coordination needed, and that simplicity is why it's popular.

Here's the problem, and it's a deep one. Each server stamps the write using its own clock. And physical clocks on different machines are never perfectly in sync. They drift, they get corrected by time-syncing services that can jump them forward or backward, and across a fleet they can disagree by milliseconds, sometimes much more. This is called clock skew. So the timestamps you're comparing weren't measured against one shared clock, they were measured against two different, imperfect clocks that disagree about the current time.

Now watch the data loss happen. Server A's clock happens to be running a bit fast. Server B's clock is a bit slow. A user writes an important value through server B at the true time of, say, 12:00:05. A moment later, genuinely after it, another write, maybe even a less important one, goes through server A at true time 12:00:06. But because A's clock reads slightly fast and B's reads slightly slow, the timestamps recorded might say A's write happened at 12:00:04 and B's at 12:00:05. When the servers reconcile and keep the "later" timestamp, they keep B's. The write that truly happened second, the newer one, gets silently discarded because its machine's clock said an earlier time. The data is just gone, no error, no warning, and the "last" write didn't actually win, the write from the faster clock did.

The root issue is that a timestamp from a wall clock does not reliably tell you the true order of events across machines. Ordering, which thing really happened before which, is not the same as comparing two clock readings, unless those clocks are perfectly synchronized, which they never are. Last-write-wins quietly assumes a global, perfect clock that doesn't exist.

So what do careful systems do instead? They track causality directly rather than trusting wall-clock time. One tool is a version vector or vector clock: instead of a timestamp, each write carries a little record of what it was based on, which version it saw. When two writes are compared, the system can tell whether one genuinely came after the other, in which case the later one safely wins, or whether they were truly concurrent, made without knowledge of each other. And here's the key difference: when two writes are genuinely concurrent, a good system doesn't silently throw one away. It detects the conflict and keeps both, handing them to the application to merge, the way a shopping cart merges by taking the union of items rather than letting one device's cart erase the other's. The conflict is surfaced, not hidden.

"Keep the latest one" sounds unarguable, until you remember that the two machines don't agree on what time it is. The write that wins isn't the one that happened last. It's the one whose clock ran fast, and that's not a rule, that's a silent bug.
