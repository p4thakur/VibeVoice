In July 2016, Stack Overflow went down because of a single forum post. The post had about 20,000 spaces in it, and one line of regex turned those spaces into hundreds of millions of steps of work. It's called catastrophic backtracking, and it can take down any service that runs a regex on text a user typed.

The line of code was small and ordinary. When a question appears on the homepage, the site trims whitespace off the ends of the text. The regex that did it said, in plain words: match whitespace at the start of the string, or match whitespace at the end. The second half is the problem, and it's roughly: one or more whitespace characters, followed by the end of the string.

Watch the engine on a normal string, say "hello" and three trailing spaces. It reaches the spaces, matches all three, checks for end-of-string, succeeds. Fast. Now the bad post: about 20,000 spaces in a row, and then a non-space character. The engine starts at the first space and greedily eats all 20,000. Then it checks: am I at the end? No, there's a character after them. So it fails. But a backtracking engine doesn't give up. It gives back one space and checks again. Fail. Gives back another. Fail. It tries all 20,000 possible lengths, and every one fails.

Then it moves to the second space and does the whole thing again with 19,999, then the third with 19,998, and so on. The total work is 20,000 plus 19,999 plus 19,998, all the way down. That sum is n squared over two. For 20,000 spaces that's about 200 million steps, for one string. Double the spaces and the work quadruples. Linear input, quadratic cost. That's what the word catastrophic means here.

Why did one string take the whole site down? Because the post sat on the homepage question list, so every single page load ran that regex on it. Each request pinned a CPU core for a long time. Within minutes all the web servers were at 100 percent CPU. The load balancer's health checks, served by those same pegged servers, started timing out, so the balancer declared servers dead and pulled them out, which piled their traffic onto the few left, which pegged those too. The site went down for about 34 minutes. The fix was to delete the post, then fix the regex.

The deep cause is how the regex engine works. Most languages, including the one Stack Overflow used, use a backtracking engine: it tries one way to match, and when that fails it reverses and tries another. That's what makes features like backreferences possible, and it's also why the worst case can explode to quadratic or even exponential time. There's another design, used by Google's RE2, that tracks all possible matches at once and is guaranteed to run in time proportional to the input length. The price is that it can't support a few features like backreferences. For untrusted input, that's usually a price worth paying.

This wasn't a one-off. In 2019, Cloudflare had a global outage from the same class of bug: one regex in a firewall rule backtracking on certain input drove the CPU on every server to 100 percent worldwide.

So the lesson an engineer carries out of this is concrete. Never run a backtracking regex on user input without a timeout. Prefer a linear-time engine for untrusted text. And for something as simple as trimming, don't reach for a regex at all, a scan from each end is two short loops that can't blow up. The bug isn't that regex is bad. It's that a backtracking engine hides a quadratic cost behind a one-line pattern, and user input will eventually find it.

One regex. One post. 20,000 spaces, 200 million steps, and a site taken down by a line meant to remove a few blank characters.
