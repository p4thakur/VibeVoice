On July 19th, 2024, around 8.5 million Windows computers across the world crashed at almost the same moment and refused to restart. Airlines grounded flights, hospitals postponed surgeries, banks and broadcasters went dark. It wasn't a cyberattack. It was a security company's own update, a single faulty file, pushed to every machine at once, that landed in the most dangerous place code can run. The CrowdStrike outage is a masterclass in two ideas every engineer must respect: blast radius, and the special danger of kernel code.

Start with where the software lived, because that's half the story. CrowdStrike makes security software, Falcon, that runs on millions of corporate Windows machines. To detect threats effectively, part of it runs in the kernel, the innermost, most privileged core of the operating system, the layer that controls the hardware and everything else. Code in user space, where ordinary apps live, is sandboxed: if it crashes, the operating system just kills that one app and carries on. Code in the kernel has no such safety net. The kernel is the thing that does the catching, so if kernel code makes an illegal memory access, there's nothing above it to contain the fault. The whole operating system halts, that's the blue screen of death. So the first fact is that Falcon's detection engine ran in the one place where a bug doesn't crash a program, it crashes the entire computer.

Now the trigger. CrowdStrike pushed out a routine update, not to the program itself, but to its configuration, a content file telling the engine what new threats to look for. People think of updates as code and config as harmless data, but here's the thing: that config was consumed by kernel code, and it was effectively instructions the engine had to interpret. The new file was malformed in a way that, when the kernel engine processed it, caused it to read memory it shouldn't, an out-of-bounds read, accessing a location outside what it was allowed to touch. In user space that might crash one app. In the kernel, it crashed Windows itself. And because the faulty file was loaded very early, every time the machine booted, the machine would crash on startup, then reboot, then crash again, a boot loop. The computers weren't just down, they couldn't bring themselves back up.

Then the part that turned a bug into a global catastrophe: blast radius. The faulty file was pushed to essentially all Falcon machines at once, worldwide, within minutes. There was no gradual rollout, no sending it to a small percentage first, watching for problems, and only then expanding. So when the file was bad, it didn't take down one machine or one company, it took down millions, everywhere, simultaneously, before anyone could react. And because each machine was stuck in a boot loop, the fix couldn't be pushed out as another update, the machines couldn't stay up long enough to receive it. In many cases, a human had to physically touch each computer, boot it in a special mode, and delete the bad file by hand. Millions of machines, one at a time. That's why recovery took days, not minutes.

So three compounding factors, each a lesson. One: the code ran in the kernel, where a fault isn't contained, it's fatal to the whole system, so kernel code demands extraordinary caution. Two: a config file is not harmless data when privileged code interprets it, config is code, and it deserves the same testing and validation as code, because a bad config can crash you exactly like a bad program. Three, and the biggest: the update went everywhere at once, giving it a blast radius of the entire install base, with no staged rollout to catch the problem while it was still small.

Eight and a half million computers, down in minutes, from one bad file pushed everywhere at once, into the one layer where a crash takes the whole machine with it. Test your config like code, respect the kernel, and never, ever ship to everyone at the same time.
