Interview mein ek question aata hai, aur fintech companies mein toh almost har loop mein aata hai. User ka payment timeout ho gaya, lekin backend pe payment actually succeed ho chuka tha. User ne retry kar diya. Ab double debit kaise rokoge? Is video mein hum is question ko 4 failures ke through solve karenge, aur har fix mein exact table, exact constraint aur exact API call dekhenge. Aur ek baat abhi note kar lo: sirf idempotency key lagao bolna is question ka half answer hai. Poora answer end tak milega.

Pehle simple flow. Client Payment Service ko request bhejta hai. Payment Service payment gateway ko call karta hai, jise hum PSP bolte hain, jaise Razorpay ya Stripe. PSP customer ka paisa debit karta hai, response aata hai, aur hum apne database mein status success likh dete hain. Laptop pe yeh perfectly chalta hai. Ab dekhte hain production mein yeh kahan fail hota hai.

Failure number 1: client ka retry. Network timeout hua, client ko response nahi mila, toh woh dobara request bhejta hai. Server ko lagta hai yeh naya payment hai, aur doosra debit ho jaata hai. Fix hai idempotency key. Client har logical payment ke liye ek UUID generate karta hai, jaise Pay button click hote hi, aur usse header mein bhejta hai. Retry mein wahi key jaati hai. Ab yahan sabse common galti suno. Candidates key ko Redis mein SET with NX se store karte hain aur sochte hain kaam ho gaya. Lekin Redis restart ho gaya, ya key expire ho gayi, ya process charge ke baad aur Redis write se pehle crash ho gaya, toh duplicate seedha andar aa jaata hai. Real guard database ka UNIQUE constraint hai.

Design yeh hai. PostgreSQL mein ek idempotency table, jisme key, request ka hash, status aur stored response ke columns hain, aur key pe UNIQUE constraint. Payment aate hi pehla step: is table mein INSERT karo, status IN PROGRESS. Doosra request wahi key insert karega toh constraint fail, aur hume pata chal jaata hai ki duplicate hai. Aur yeh insert payment row ke saath ek hi transaction mein hona chahiye. Agar key ek jagah likhi aur payment row doosri jagah, toh beech mein crash hone par idempotency break ho jaati hai.

Retry aane par teen cases hote hain. Key IN PROGRESS hai: matlab pehla request abhi chal raha hai, toh 409 conflict return karo ya result ka wait karo. Key COMPLETED hai: stored response wapas return karo, naya charge bilkul nahi. Aur key same hai lekin request body alag hai, jaise amount change ho gaya: yeh client ka bug hai, reject karo. Isiliye request ka hash store karte hain.

Failure number 2: yahi interview ka asli sawaal hai. Payment Service ne PSP ko call kiya, PSP ne paisa debit kar diya, aur ussi beech mein Payment Service crash ho gaya, ya PSP ka response timeout ho gaya. Humare database mein status PROCESSING pada hai. Hum nahi jaante ki paisa gaya ya nahi. Isko unknown state kehte hain, aur poora design isi ke around banta hai. Ab pause karo. Is state mein aap kya karoge? Fail mark karke user ko retry karne doge, ya dobara charge kar doge? Comment mein likho.

Dono galat hain. Fail mark kiya aur paisa actually gaya tha, toh user ko pata nahi chalega aur support tickets aayenge. Dobara charge kiya, toh double debit. Sahi tareeka: payment ko ek state machine banao. CREATED, PROCESSING, SUCCESS, FAILED, aur ek explicit state UNKNOWN. Timeout aane par status UNKNOWN set karo. Phir ek background worker PSP ka status check API call karta hai, aur result ke hisaab se SUCCESS ya FAILED mark karta hai. Aur ek rule hamesha yaad rakho: PSP ko call karne se pehle payment row ko PROCESSING status ke saath database mein commit karo. Phir call karo. Taaki crash ho jaaye toh bhi humare paas ek record ho jise baad mein verify kar sakein.

Aur agar retry karna hi hai, toh PSP ko wahi idempotency key forward karo. PSP ke paas apna idempotency mechanism hota hai, Stripe mein Idempotency Key header hai. Matlab idempotency end to end honi chahiye: humari key PSP ki key se mapped. Warna guarantee sirf humare system tak hi rehti hai, aur paisa phir bhi double move ho sakta hai.

Failure number 3: webhooks. PSP payment ka final result webhook se bhejta hai. Webhooks retry hote hain, duplicate aate hain, aur kabhi order mein nahi aate. FAILED ka event SUCCESS ke baad aa sakta hai. Fix mein do cheezein hain. Pehli: har webhook ka event id table mein UNIQUE constraint ke saath store karo. Same event dobara aaye toh ignore. Doosri: status sirf aage ki direction mein badalna chahiye. Update statement aise likho: UPDATE payments SET status equals SUCCESS WHERE id match kare AND status PROCESSING ya UNKNOWN ho. Agar payment already SUCCESS hai toh zero rows update hongi, aur late aaya FAILED event kuch affect nahi karega. Aur webhook handler ko jaldi 200 return karna chahiye, heavy kaam queue mein daal do, warna PSP samjhega ki fail hua aur retry karega.

Failure number 4: sab kuch sahi kiya, phir bhi kuch payments mismatch rehte hain. PSP ke records mein SUCCESS, humare mein FAILED. Isliye reconciliation. Har din PSP ki settlement file humare records se match karo, aur mismatch ke liye alert ya auto fix chalao. Staff level answer mein reconciliation bolna mandatory hai, kyunki yeh batata hai ki aapne kabhi real money system chalaya hai. Aur balance ka kya? Kabhi UPDATE balance SET amount equals amount minus 100 mat likho. Double entry ledger banao: har transaction ke do rows, ek debit aur ek credit, ek hi database transaction mein, aur dono ka sum zero. Isse har rupaya traceable hai aur audit possible hai.

Ab interviewer ke follow-up questions. Idempotency key kaun generate kare, client ya server? Client, kyunki retry pe server ko pata hi nahi hota ki yeh same operation hai. Key kitne time tak store karein? Retry window se zyada, jaise 24 ghante, permanent nahi, warna table bahut badi ho jaayegi. Aur agar operation charge se pehle fail ho gaya, toh key ka kya? Us row ko FAILED mark karo aur decide karo ki client naya key use karega ya retry allowed hai. Yeh ek design decision hai, aur interview mein isse explicitly bolna chahiye.

Ab level ke hisaab se expectation, meri understanding ke mutabiq. SDE 2 se expect hota hai ki aap idempotency key, database ka UNIQUE constraint aur webhook handling tak pahunchein. SDE 3 se expect hota hai ki aap unknown state ko state machine se handle karein, PSP call se pehle record persist karein, idempotency ko PSP tak end to end rakhein, aur reconciliation aur double entry ledger khud bolein, interviewer ke poochne se pehle.

Ek line mein yaad rakho: key ko database mein UNIQUE se lock karo, call se pehle record likho, unknown state ko name do, aur daily reconcile karo.
