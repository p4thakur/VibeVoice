A database crashes mid-transaction, the power dies with your money half-moved between accounts, and yet when it boots back up, your balance is perfect. Not approximately. Exactly. The thing that makes that possible is a rule so simple it sounds like nothing: before you change anything, write down what you're about to do. It's called the write-ahead log, and it's the quiet foundation under the D in ACID, durability.

Start with why the obvious approach fails. Say you want to update a row. The naive way is to go to that row's page on disk and overwrite it in place. But a single logical change often touches several places, move money between two accounts, and you must update both. What if the power dies after you've written the first and before the second? Now one account was debited and the other was never credited. Money vanished. Worse, writing even a single page to disk isn't guaranteed to be all-or-nothing, a crash mid-write can leave a page half-old, half-new, corrupt, a torn write. In-place updates give you no way to recover a consistent state after a crash, because you've destroyed the old data without any record of what you were trying to do.

The write-ahead log fixes this by inverting the order. Before touching the actual data, the database first appends a record to a log, a separate file, describing the change it's about to make: "set account A to this value, set account B to that value." This log is append-only, you only ever add to the end, never go back and edit. Only after that log record is safely on disk does the database apply the change to the real data pages. The rule, in one line: write the intention to the log before you perform the action. That's the whole idea, and the ordering is everything.

Now watch it save you. Suppose the power dies. When the database restarts, it reads through the log. For any transaction whose log records are complete, it re-applies those changes to the data, this is called replaying the log, making sure every committed change actually made it into the data. For any transaction whose log records are incomplete, it was still in progress at the crash, so it undoes any partial effects, rolling it back as if it never happened. Either way, you end up in a clean, consistent state: every transaction is either fully done or fully gone, never half. The log is the source of truth the database uses to repair itself, because it recorded what should happen before the messy business of making it happen.

There's a performance bonus hiding in here, which is why this isn't just a safety tax. Appending to a log is a sequential write, the fastest thing a disk does, as we've seen. The actual data pages, scattered around the disk, can be updated more lazily, in the background, batched up, because the log already guarantees durability. So the database can tell you "committed, your data is safe" the instant the log record is on disk, without waiting to carefully update every scattered data page first. Many systems even batch many transactions' log records and flush them together in one disk write, called group commit, trading a tiny bit of latency for much higher throughput. The log turns a pile of slow random writes into one fast sequential write plus cleanup-at-leisure.

This pattern is everywhere once you see it. Postgres calls it the WAL. Other databases call it a redo log or a transaction log. Filesystems use the same idea under the name journaling, a journaling filesystem writes what it's about to do to a journal first, which is why modern filesystems survive a crash without the long, scary disk checks older ones needed. Even the LSM trees we discussed start every write with a log append for exactly this durability reason.

Power dies mid-transfer, and your balance is still perfect. Not luck. The database wrote down what it was going to do before it did it, so when the lights came back, it knew exactly how to finish the job or pretend it never began.
