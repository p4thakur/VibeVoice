Redis, one of the fastest databases in the world, handling hundreds of thousands of operations a second, does its core work on a single thread. One. In an age of processors with dozens of cores, the thing famous for speed deliberately ignores almost all of them. That sounds like a mistake, and understanding why it's actually the source of Redis's speed overturns a lot of lazy assumptions about what makes software fast.

Start with the instinct this violates. We're taught that to go fast, you use many threads, so the work spreads across many cores in parallel. For CPU-heavy work, like crunching numbers, that's true. But Redis asked a sharper question: what is actually the bottleneck here? Redis keeps all its data in memory, and its operations are mostly simple, set this key, get that key, add to this list. Each one is a tiny amount of work on data that's already in RAM, so each takes microseconds. The processor is never the thing holding Redis back. The limits are how fast it can read and write memory and how fast it can move data over the network. The CPU spends most of its time waiting on those, not computing.

Now, here's what multithreading would cost in that situation. If many threads all touched the same in-memory data at once, you'd need locks to stop them from corrupting each other, two threads incrementing the same counter at the same moment can lose an update. Locks mean threads waiting for each other, and the machinery of locking itself burns time. On top of that, switching the processor between many threads has a cost, called a context switch: each switch saves one thread's state and loads another's, and thrashes the CPU's caches. For work where each operation is only microseconds, the overhead of coordinating threads and switching between them can easily cost more than the actual work. You'd add a lot of coordination machinery to speed up work that was never CPU-bound in the first place.

So Redis makes the opposite bet: one thread, no locks, no coordination, no context-switching between workers. And it stays busy serving thousands of simultaneous connections using a technique we've met, an event loop built on epoll. Instead of one thread per connection sitting idle waiting, a single thread asks the operating system "which of my thousands of connections have data ready right now?" and the OS hands back just the ready ones. The thread rips through them one after another, each operation so fast that clients barely wait their turn. Because there's only one thread, there's nothing to lock, so each Redis command runs to completion atomically, with no other command interleaving, which also makes Redis's behavior simple to reason about, a quiet but huge benefit.

This design has a sharp edge, and it's the thing to know if you run Redis. Because everything runs on one thread, in order, one slow command blocks everything behind it. If you run a command that has to examine a million keys, or sort a giant list, that single command hogs the one thread, and every other client, with their microsecond-fast requests, is stuck waiting behind it. In a multithreaded system, a slow query ties up one thread while others keep serving. In single-threaded Redis, a slow command is a stall for everyone. So the operational rule is: never run expensive, sweeping commands on a production Redis, break big operations into small pieces. The simplicity that makes it fast is the same property that makes one bad command freeze the whole server, the recurring theme that a mechanism's strength and weakness are one fact seen from two sides.

Modern Redis has added some threads, but notice where: for network input and output, reading and writing socket data, which was becoming a bottleneck at very high throughput. The actual command execution, the touching of your data, stays on the one main thread, precisely to keep the no-locks, no-coordination simplicity intact. They threaded the part that was I/O-bound and kept the part that benefits from being serial, serial.

Hundreds of thousands of operations a second, on one thread, on purpose. Not because parallelism is bad, but because when the work is already in memory and takes microseconds, the cost of coordinating many threads is bigger than the work itself. Know your bottleneck before you reach for more threads.
