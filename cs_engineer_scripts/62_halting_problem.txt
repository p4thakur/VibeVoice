You can never write a program that looks at any other program and tells you, reliably, whether it will eventually finish or run forever. Not because we're not clever enough yet. Because it's been proven impossible, forever, by Alan Turing in 1936, before computers even existed. It's called the halting problem, and it's not an abstract curiosity. It's the reason your antivirus can never be perfect and your compiler can never catch every bug.

First, what's being claimed, precisely. It would be incredibly useful to have a checker, call it a function, that takes any program and its input, and returns one of two answers: "this will halt," or "this will run forever." Think how handy that is. You could detect infinite loops before shipping. You could prove code terminates. The claim is that no such checker can exist that is always correct for every possible program. You can write checkers that work for many programs, but none that works for all of them.

Now the proof, and it's one of the most beautiful arguments in all of mathematics, because it needs no hardware, just logic. Suppose, for contradiction, that the perfect checker does exist. Call it H. Give H a program and an input, and it always correctly says halts or loops forever.

If H exists, we can build a new, mischievous program out of it. Call it D, for devil. D takes a program as its input, and here's what D does: it runs H to ask, "does this program halt when fed a copy of itself as input?" Then D does the opposite of H's answer. If H says "that program halts," then D deliberately goes into an infinite loop. If H says "that program loops forever," then D immediately halts. D is built to contradict whatever H predicts.

Now the killing stroke. Feed D a copy of itself. Ask: does D, running on D, halt? Walk through it. Inside, D asks H what D does when run on D, the very question we're asking. Suppose H answers "it halts." Then by D's own rule, D does the opposite and loops forever, so H was wrong. Suppose instead H answers "it loops forever." Then by D's rule, D halts immediately, so H was wrong again. Whatever H says, D does the opposite, so H's answer is wrong in every case. But we assumed H was always correct. That's a flat contradiction. So our assumption must be false: the perfect checker H cannot exist. This technique, building a thing that asks about itself and then contradicts the answer, is called diagonalization, and it's the same shape of argument that proves some infinities are bigger than others.

This isn't a loophole you can engineer around. A broader result called Rice's theorem extends it: essentially any interesting question about what a program does, not how it's written, but what it actually computes, is undecidable in general. Will this program ever access this file? Will it ever produce this output? Is it free of this class of bug? In full generality, provably unanswerable.

So what does an engineer actually do with this? You accept that general-purpose program analysis must be imperfect, and you design around it honestly. This is why static analyzers and type checkers are conservative: they'll warn about code that's actually fine, because the alternative, missing real problems, is worse, and perfection is off the table. It's why antivirus can't just decide whether a file is malicious by analyzing what it'll do, so it leans on signatures, sandboxes, and timeouts instead. It's why your build tools can't guarantee your code terminates. And it's why, in practice, we bound the unknowable: we don't ask "will this ever finish," we say "if it hasn't finished in 30 seconds, kill it." The timeout is an admission, baked into real systems everywhere, that some questions can only be answered by waiting, because they can't be answered by thinking.

A proof from 1936, with no computer in sight, that draws a hard edge around what computers can ever do. Not slow to answer. Impossible to answer. And knowing where that edge is tells you when to stop looking for a perfect checker and reach for a timeout instead.
