A database can find one specific row among a billion in about four disk reads. Not four hundred, not forty. Four. The structure that pulls this off is the B-tree, and understanding it means understanding one hard truth about computers: the slow part isn't thinking, it's reaching the data, so you design everything around touching the disk as few times as possible.

Start with that truth. Reading from a disk, even a fast SSD, is thousands of times slower than anything the processor does in memory. So for a database searching on disk, the thing to count isn't comparisons, it's reads, how many times do I have to go fetch a chunk from storage. The whole game is to answer a query in the fewest fetches.

Now, you might reach for a binary search tree, where each node has two children and each step halves the search. For a billion rows, halving takes about 30 steps, since two to the 30 is a bit over a billion. But in a disk-based tree, each step down means following a pointer to a different node, and each node lives in a different spot on disk. So 30 steps is potentially 30 separate disk reads for one lookup. Thirty times the slowest thing the machine does. Too slow.

Here's the B-tree's key move. Disks don't read one byte at a time, they read in fixed blocks, called pages, typically about 8 kilobytes, because the cost is dominated by finding the data, not by how much you grab once you're there. So reading 8 kilobytes costs essentially the same as reading 8 bytes. The B-tree exploits this: instead of putting one key and two child-pointers in a node, it makes each node a full page and crams it with hundreds of keys and hundreds of child-pointers. So from one node, you don't branch two ways, you branch, say, a few hundred ways, all for the price of a single disk read of that one page.

That high fan-out is what crushes the height of the tree. The number of reads to reach any row is the height of the tree, and the height is how many times you multiply the fan-out to reach a billion. With a fan-out of around 300, one level covers 300 rows, two levels cover 90,000, three cover 27 million, and four levels cover 8 billion. So a billion-row table is about four levels deep. Four levels means four disk reads to find any row, down from thirty. Each read, though, now hands you a page with hundreds of keys, which you scan in fast memory to decide which pointer to follow next. You've traded cheap in-memory comparisons, of which you do a few hundred per level, for expensive disk reads, of which you now do only four. That's exactly the right trade, because memory is fast and disk is slow.

Real databases use a refinement called a B-plus-tree, where the actual row data lives only in the bottom level, the leaves, and the leaves are linked together in order like a chain. That linking adds a second superpower: range queries. Because the leaves are sorted and chained, "give me every order between March and June" means find the start with four reads, then just walk along the chain of leaves, instead of jumping around the tree for each row. That ordered structure is also why a B-tree index speeds up sorting and "greater than" queries, and why it's the default index in essentially every relational database.

And this tells you when a B-tree is the wrong tool, which is the interview-worthy flip side. If all you ever do is look up single keys by exact match, never ranges, never sorted scans, a hash index can do it in one read instead of four, because a hash jumps straight to the location. The reason databases still default to B-trees is that real queries constantly ask for ranges and order, "all users who signed up this week," "the top ten by score," and hashes can't do those at all. You pick the structure by the shape of your queries: B-tree for order and ranges, hash for pure exact-match speed.

A billion rows, four reads. The B-tree doesn't win by being clever about comparing. It wins by knowing that the disk is the enemy, that the disk hands you a whole page at a time, and by packing each page so full that the tree is only four levels tall.
