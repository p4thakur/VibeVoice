Interviewer bolta hai: aisa system design karo jo user ke 10 kilometer ke andar ke saare restaurants dhundhe. Yeh ek simple database query lagti hai, aur isi question pe candidates atak jaate hain. Microsoft ne iska ek version poocha, aur Amazon Locker wale question ka core bhi yahi hai: nearest store dhundho. Is video mein hum ise failure by failure solve karenge, aur aapke paas SDE 2 ya SDE 3 interview ke liye clear answer hoga.

Pehle naive attempt. Aap latitude aur longitude PostgreSQL table mein store karte ho, aur likhte ho: WHERE user se distance 10 km se kam ho. Distance nikalne ke liye Haversine formula use karte ho, jisme sine aur cosine functions hote hain. Problem yeh hai ki database computed distance pe index use nahi kar sakta, toh woh har row ke liye yeh calculate karta hai. 50 lakh restaurants hain toh har search ek full table scan hai. Kuch hazaar searches per second pe system mar jaata hai.

Doosra attempt: bounding box. User ke around ek square nikalo: latitude lat minus delta se lat plus delta ke beech, longitude lon minus delta se lon plus delta ke beech. Latitude aur longitude pe B-tree index lagao. Ab query fast hai. Lekin B-tree ek dimension achhe se handle karta hai. Woh latitude se narrow karke earth ki ek lambi horizontal strip de deta hai, aur phir bhi longitude se millions rows filter karni padti hain. Do alag one-dimensional indexes se two-dimensional index nahi banta.

Ab pause karo. Two-dimensional location ko aise cheez mein kaise badloge jo normal index search kar sake? Apna idea comment mein likho.

Answer hai: duniya ko cells mein baanto, aur har location ko ek cell ID do. Sabse popular tareeka geohash hai. Geohash map ko grid mein split karta hai, phir har cell ko baar baar split karta hai, aur result ko ek chhoti string mein encode karta hai. Magic property: paas ki jagahon ka common prefix hota hai. Prefix jitna lamba, cell utna chhota. 5 character ka geohash roughly 5 kilometer by 5 kilometer ka cell hai, aur 4 character wala roughly 39 by 20 kilometer ka. Ab location search ek string prefix search ban gaya, jo normal index fast kar leta hai.

Toh plan: har restaurant ko uske geohash ke saath store karo. 10 km search ke liye user ka cell nikalo, us cell ke restaurants fetch karo, aur phir exact distance se filter karo. Lekin yahan aata hai failure number 2: boundary problem. User cell ke edge pe khada ho sakta hai. Sirf 200 meter door ka restaurant neighboring cell mein ho sakta hai, jiska prefix bilkul alag hai. Sirf user ka cell search karoge toh woh miss ho jayega. Isliye hamesha user ka cell plus uske 8 neighbors search karo, yaani 9 cells. Phir candidates ka exact distance nikalo, 10 km se door wale hatao, distance se sort karo, aur return karo. Yeh line yaad rakho: grid candidates dhundhta hai, exact distance answer deta hai.

Failure number 3: cell size choose karna. Cells bahut bade hon toh har search hazaaron candidates kheenchti hai aur exact distance filter hi cost ban jaata hai. Bahut chhote hon toh 10 km radius ke liye darjano cells chahiye. Radius ke hisaab se precision pick karo, taaki search ek chhote, fixed number of cells touch kare. Yeh baat interview mein bolna achha hai.

Failure number 4: uneven density. Mumbai ke ek cell mein hazaaron restaurants hain, aur kisi desert mein zero. Uniform grid dono ko same treat karta hai. Yahan quadtree help karta hai: woh cell ko tabhi split karta hai jab usme bahut zyada points hon, toh dense areas ko fine cells milte hain aur sparse areas ko bade. Uber ka H3 aur Google ka S2 similar ideas hain, better geometry ke saath: H3 hexagons use karta hai taaki saare neighbors same distance par hon. Inhe implement karne ki zaroorat nahi, lekin naam lena strong signal hai.

Ab actually kaunsa tool use karoge? Teen achhe answers hain. Restaurants jaisi static places ke liye PostgreSQL mein PostGIS ka spatial index hota hai, GiST index, aur ST_DWithin jaisi queries fast chalti hain. Elasticsearch mein bhi geo_distance query hai, aur jab text search aur filters bhi chahiye, jaise cuisine ya rating, tab yeh useful hai, jo ek food app ko chahiye hi hota hai. Aur fast-moving objects, jaise delivery partners ya cabs, ke liye Redis GEO use karo. Redis locations ko sorted set mein store karta hai, geohash ko score banakar. GEOADD location add karta hai aur GEOSEARCH radius ke andar sab dhundh deta hai. Yeh in-memory hai, toh constant location updates handle kar leta hai.

Yeh farq hi real insight hai: static data versus moving data. Restaurants kam badalte hain, toh unhe PostGIS ya Elasticsearch mein index karo aur popular cells cache karo. Drivers har kuch seconds mein move karte hain, toh unki latest location Redis mein rakho, aur TTL lagao taaki jo driver offline ho jaye woh apne aap hat jaye. Har GPS ping ko main database mein mat likho.

Failure number 5: scale. Ek Redis ya ek database poori duniya nahi hold kar sakta. Geography se shard karo. Geohash prefix ya city ko shard key banao, taaki ek search ek shard touch kare, ya zyada se zyada kuch. Lekin hotspots se bacho, kyunki dinner time pe Mumbai kisi chhote town se kahin zyada hot hai. Hot regions ko chhote cells mein split karke, ya bade cities ko apne alag shards dekar handle karo. Read replicas bhi help karte hain, kyunki reads dominate karte hain.

Agar interviewer Amazon Locker style question pooche, yaani available slots wala nearest store dhundho, toh answer wahi grid hai, ek extra step ke saath: candidates ko distance se sort karne se pehle availability se filter karo.

Ab expectations. SDE 2 se expect hota hai ki aap full table scan reject karo, geohash ya similar grid explain karo, aur neighbor cells handle karo. SDE 3 se expect hota hai ki boundary problem aur uneven density khud bring up karo, static aur moving data ko alag karo, PostGIS, Elasticsearch aur Redis GEO jaise tools choose karo, aur geography se shard karna explain karo.

Ek line mein yaad rakho: two dimensions ko cell IDs mein badlo, cell aur uske neighbors search karo, phir exact distance se filter karo. Agar is video ke notes chahiye toh comment mein NEARBY likho, main breakdown bhej dunga. Aur comments mein batao ki kaunsa interview question aapko sabse zyada pareshan karta hai.
