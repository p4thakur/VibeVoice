Twitter needed to give every tweet a unique ID, thousands per second, generated across hundreds of machines that never talk to each other, and the IDs had to come out roughly in time order. A plain database counter couldn't do it. Random UUIDs couldn't do it. So they designed a 64-bit number with a very deliberate internal structure, called Snowflake, and it's a masterclass in getting several guarantees at once by carefully dividing up the bits of a single number.

Start with why the easy options fail. A database counter, 1, 2, 3, gives you unique, time-ordered IDs, but it needs one central authority to hand out the next number, and that authority becomes a bottleneck and a single point of failure when you're making thousands of IDs a second across many servers. Random UUIDs solve the coordination problem, every machine makes its own with no bottleneck, but they come out in random order, which, as we've seen, scatters database inserts all over the index and kills write performance. Twitter wanted all three things together: no central coordination, guaranteed uniqueness, and rough time-ordering so IDs sort by when they were made.

The Snowflake answer is to take a 64-bit integer and slice it into sections, each section carrying a different piece of meaning. Think of the 64 bits as a number line you carve into three zones.

The first and largest zone, about 41 bits, holds a timestamp: the number of milliseconds since a chosen starting moment. Put the timestamp in the high bits, the most significant part of the number, and you get time-ordering for free, because a tweet made later has a larger timestamp, which makes the whole number larger, so sorting the IDs numerically sorts them by time. 41 bits of milliseconds, by the way, is about 69 years of range, enough to last the life of the system.

The second zone, about 10 bits, is a machine identifier: a number assigned to each ID-generating server, from 0 up to 1,023. This is the trick that removes coordination. Because every machine stamps its own unique ID into this zone, two different machines can generate IDs at the very same millisecond and still never collide, their IDs differ in the machine-ID bits. No machine has to ask any other machine anything.

The third zone, about 12 bits, is a per-machine sequence counter. Within a single millisecond, one machine might need to make several IDs. So it counts them: 0, 1, 2, up to 4,095, that's what 12 bits holds. This guarantees uniqueness even for many IDs from the same machine in the same millisecond. If a machine somehow needs more than 4,096 IDs in one millisecond, it simply waits for the next millisecond and resets the counter.

Put the three zones together and every piece of the guarantee is accounted for. Two IDs from different machines differ in the machine zone. Two from the same machine in the same millisecond differ in the sequence zone. Two from different times differ in the timestamp zone. So the whole 64-bit number is always unique, with no coordination between machines, and because the timestamp sits in the top bits, the IDs sort by creation time, which keeps database inserts neat and local instead of scattered. One number, three jobs, done by giving each job its own bits.

Thousands of IDs a second, hundreds of machines, zero coordination, and they still sort by time. Not magic, just a 64-bit number with its bits divided up on purpose.
