Add one server to a 100-server cache, and 99 percent of your keys vanish in the same instant. The fix is consistent hashing, and it's worth understanding down to the exact operation your code runs, because this is the question behind half of all "how would you shard this" interview answers.

Start with the obvious way to spread keys across servers. Take the key, hash it to a big number, and compute hash modulo N, where N is the number of servers. With 100 servers every key lands on a server from 0 to 99. It's fast, it's even, and it works perfectly until the day N changes.

Add one server, so N goes from 100 to 101. Now recompute hash mod 101 for a key. The remainder is almost always different from hash mod 100, because you changed the divisor, and the divisor touches every key. Work it out and only about 1 key in 101 keeps its old home. So 99 percent of your keys now point at the wrong server. Every one of those is a cache miss, all at once, and that whole flood of traffic crashes straight through to your database in the same second. Adding a machine to help with load is the thing that takes you down. That's the trap.

Consistent hashing changes the question from "which of N slots" to "where on a circle." Picture a ring of numbers, say 0 up to about 4 billion, wrapping around. You hash each server's name to a point on that ring. You hash each key to a point on the same ring. A key belongs to the first server you hit walking clockwise from the key's point.

Now, how does your code actually find that server, because this is the mechanism the original story always skips. You keep the servers' points in a sorted array. To place a key, you hash it and do a binary search for the next server point clockwise. That's an O(log n) lookup, a handful of comparisons even for thousands of servers. No modulo over N, so nothing depends on the count the way mod N did.

Here's the payoff. Add a new server, and it hashes to one point on the ring. It takes over only the arc between itself and the previous server going counter-clockwise, the keys that used to walk past that gap to the next server. That's roughly 1 in N of the keys. Everyone else is exactly where they were, because their clockwise walk never changed. Remove a server and only its arc moves, to the next server along. So the cost of scaling drops from 99 percent of keys reshuffled to about 1 percent. That number, the fraction of data that moves when the cluster changes, is the entire reason this exists.

But there's a flaw, and the fix for it is the part people wave their hands at, so let's not. If you drop 100 servers onto the ring at random, the gaps between them are wildly uneven. One server might own a huge arc and get hammered while its neighbor owns a sliver and sits idle. Randomly placed points just aren't evenly spaced. The fix is virtual nodes: instead of hashing each server to one point, you hash it to many, often a couple hundred. Each physical server now owns a few hundred small arcs scattered all around the ring, and by the law of large numbers those even out. The more virtual nodes per server, the tighter the balance, roughly by the square root of their number, so a few hundred gets you load within a few percent of even. Dynamo and Cassandra both do exactly this.

And there's one thing virtual nodes do not fix, which is the honest tradeoff to name. Consistent hashing balances keys, not traffic. If a single key goes viral, one celebrity's record, one hot product, all its requests hash to the same point and hammer one server no matter how many virtual nodes you have. That's the hot-key problem, and it needs a different tool: replicating that key across several nodes, or a bounded-load variant that spills a key to the next node once its owner is full. Knowing that limit, and naming it before the interviewer does, is what separates "I memorized consistent hashing" from "I've been bitten by it."

The idea came from a 1997 MIT paper by David Karger and colleagues, built to spread web load, and it became the foundation of Akamai's CDN. Today it's how Dynamo, Cassandra, and most distributed caches decide where your data lives.

Same servers, same keys. Turn the row of slots into a circle, binary-search to the next point clockwise, and scatter each server across it a few hundred times. Growth stops being a disaster and becomes a one percent move.
