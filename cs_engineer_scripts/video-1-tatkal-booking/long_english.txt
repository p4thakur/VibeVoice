Let's try something. Imagine you've been asked to build IRCTC's Tatkal booking system. Tatkal is the last-minute quota, and it opens at 10 AM for AC classes, one day before the journey. You build a design that works perfectly on your laptop. Then 10 AM arrives, 300,000 people click at the same moment, and your system breaks in 4 different ways. We'll walk through those 4 failures one by one, and for every fix you'll see the exact tool and the exact command. These are the 4 places where interviews put you under pressure, and each time I'll tell you what the interviewer is going to ask.

First, a clarifying question you should ask early in the interview. Does the user pick a specific seat? In Tatkal, usually not. The user gives a train, a date, a class and the passengers, and the system allots the berth. That one question changes the whole design. There's no seat map, so we don't need to track every seat. We need one counter: how many seats are left for this train, this date, this class, in the Tatkal quota. Inventory is a counter, and booking means decrementing it. The second question: how consistent does it need to be? The counter must never go above capacity, so no overbooking. But the screen that shows availability can be slightly stale.

Now design version 1. A client, a load balancer, a Booking Service and PostgreSQL. One inventory table with train number, date, class, quota, capacity and booked. When a booking comes in, a single SQL statement runs: UPDATE inventory SET booked equals booked plus 2, WHERE the train and date match, AND booked plus 2 is less than or equal to capacity. If one row was updated, the booking succeeded. If zero rows were updated, it's sold out. That statement is atomic, so overbooking is impossible. This is the first thing interviewers check: don't read and then write, because someone sneaks in between. Put the condition inside a single update statement. This design is correct. Now let's see where it fails.

Failure number 1: a single row. 300,000 users, one inventory row, and PostgreSQL processes updates to one row one after another. The database CPU looks low, but latency is very high, because every transaction is waiting on the row lock. Now pause. One row, 300,000 requests. What would you do? Sharding, a read replica, or a bigger machine? Write your answer in the comments.

Here's the answer. Sharding won't help, because one row lives on one shard. A read replica only helps reads. A bigger machine can't remove a row lock. The real answer is this: the requests that are going to lose should never reach the database. Say the Tatkal quota for one class on one train is 100 seats. Out of 300,000 requests, only 100 will win. Taking the other 299,900 to the database is a waste.

The fix: make Redis the gate. Keep a copy of the inventory counter in Redis. When a booking request arrives, a Lua script runs first: if the counter is 2 or more, decrement it by 2 and return success; otherwise fail. Why Lua? Because the check and the decrement must happen in one atomic step, and Redis is single-threaded, so two requests can't interleave. One Redis instance handles around 100,000 operations per second, so this gate filters 300,000 requests in a few seconds. Only the winners go on to PostgreSQL.

Now the interviewer will ask: what if Redis crashes and the counter is lost? The answer: never make Redis the source of truth. PostgreSQL is the source of truth, and Redis is just a gate. If Redis restarts, rebuild the counter as capacity minus booked minus active holds. And because the conditional update still exists in PostgreSQL, even a wrong Redis counter can't cause overbooking. At worst, a few people reach payment and then fail, which is a bad user experience but not bad data.

Failure number 2: payment. A winner has to pay, and that can take 5 minutes. The counter has already been decremented, but the booking isn't confirmed. If the user abandons payment, how do the seats come back? This is where most people go wrong: they keep a database transaction open during payment. Then every user holds a connection, the connection pool is exhausted, and the whole system hangs. We don't keep the transaction open. We create a hold.

The Booking Service inserts a row in the bookings table with status pending and an expiry 10 minutes from now. It also puts a message on SQS with a 10-minute delay. In a delay queue, the message stays invisible to consumers until the time is up. Note that the maximum delay in SQS is 15 minutes, so keep the hold at 10. After 10 minutes, a worker picks up the message and checks: is the booking confirmed? If yes, do nothing. If not, mark it expired and add 2 back to the Redis counter. Why is this better than a cron job? A cron job runs every minute, scans the table each time, and releases late. Here, every hold is released at its exact expiry time, event driven.

Now the payment itself. The client talks to a payment gateway, like Razorpay or Stripe. The card details never pass through our server. After payment, the gateway calls our webhook. The webhook runs a single PostgreSQL transaction. First statement: increase booked in the inventory table, with the same conditional check. Second statement: set the booking status to confirmed, WHERE the id matches AND the status is pending. That last condition is very important, because gateways retry webhooks, and the pending condition means a second call changes nothing. That's idempotency. And what if the payment arrives after 10 minutes, once the hold has expired? The webhook tries the Redis gate again. If seats are available, confirm. If not, issue an automatic refund.

Failure number 3: the seats are sold out, but 300,000 people keep refreshing, and every refresh goes through the whole stack. The fix is to make the losing path as cheap as possible. The moment the Redis counter hits zero, set a sold-out flag, and answer from the API Gateway or the CDN edge with a regret or waiting-list response, without touching the Booking Service or Redis. For retries, use exponential backoff with jitter on the client. One more thing: a double click or a network retry must not create two holds. So the client sends an idempotency key, a UUID, with every booking attempt. The server stores that key in Redis with SET and NX. If the same key comes again, there's no new hold; the earlier result is returned.

What if the interviewer asks for even more control? Then put a virtual waiting room in front of booking. Users go into a queue, you push their position to them in real time, and for the first few seconds you admit people in random order, so the fastest network or a bot doesn't always win.

Failure number 4: bots. A script is 100 times faster than a human. Rate limiting by IP alone doesn't work, because bots keep changing IPs. So put a cost on identity: login, Aadhaar-linked verification, and an OTP on every booking. A bot needs an OTP on every attempt, and our system does no extra computation. In interviews this is called making abuse expensive. Add token bucket rate limiting at the API Gateway as well, with counters in Redis, per user and per device.

Two small things. For the availability screen, read the counter from Redis with a 2-second cache, because a slightly stale value is fine here. Cache train details like route and timings with a long TTL. And anything that isn't on the critical path after booking, like the e-ticket PDF and the SMS, goes to SQS or Kafka. The critical path has only 3 things: the Redis gate, the hold, and payment confirmation.

One thing to be clear about. IRCTC's exact internal architecture isn't public. This is the design that's expected in this kind of interview.

Now, what's expected at each level, based on my understanding. At SDE 2 you're expected to ask clarifying questions, model the inventory correctly, prevent overbooking with a conditional update, and reach a hold with expiry. At SDE 3 you're expected to bring up the Redis gate and its failure case yourself, explain why holding a database lock during payment is wrong, use delayed messages for expiry, and propose idempotency and a cheap sold-out path, and state the trade-off of every choice. And at both levels, the biggest marks go to candidates who say what will fail before the interviewer asks.

In one line: let only the winners reach the database, filter with Redis, expire holds with a delay queue, and keep the losing path cheap.
