Interview mein tab tak sab kuch smooth chalta hai, jab tak aap bolte ho: main yahan Redis ka distributed lock use karunga. Phir interviewer ek sawaal poochta hai: lock ka TTL expire ho gaya aur purana client abhi bhi kaam kar raha hai, toh? Ya seedha: kya Redis lock safe hai? Yahin pe SDE 2 aur SDE 3 ka farq dikhta hai. Is video mein hum is question ko ek story ki tarah solve karenge, aur end mein aapke paas ek aisa answer hoga jo interviewer ko sach mein impress karega.

Pehle ek simple Redis lock. Client ek command chalata hai: SET lock key, ek unique value, NX aur PX 30000. NX ka matlab sirf tab set karo jab key exist na kare. PX 30000 ka matlab 30 second baad key khud expire ho jaaye. Jo client SET successfully kar leta hai, usne lock le liya. Kaam khatam hone par woh lock release karta hai, lekin ek zaroori detail: release karte time pehle check karo ki lock ki value meri hi hai, aur tabhi delete karo. Yeh check aur delete ek Lua script mein atomic hona chahiye. Warna ek client doosre client ka lock delete kar sakta hai. Yeh pehli galti hai jo candidates karte hain.

Ab TTL kyun? Kyunki agar client crash ho gaya aur lock release nahi hua, toh woh lock hamesha ke liye stuck rahega. TTL isse bachata hai. Lekin yahin se asli problem shuru hoti hai.

Failure number 1: lock expire hua, client abhi bhi alive hai. Client A ne lock liya, TTL 30 second. Phir A ko ek long GC pause aaya, ya network mein delay, ya process kuch der ke liye freeze ho gaya. 30 second guzar gaye, lock expire ho gaya. Client B ne lock le liya aur database mein write kar diya. Ab A resume hota hai, usse lagta hai ki lock abhi bhi uske paas hai, aur woh bhi write kar deta hai. Do clients ne ek saath protected resource ko modify kiya, aur data corrupt ho gaya. Martin Kleppmann ne 2016 mein isi scenario ko explain kiya tha, aur yeh kisi bug ki wajah se nahi, sirf timing ki wajah se hota hai.

Ab pause karo. Is problem ko fix karne ke liye aap kya karoge? TTL bada karoge, ya kuch aur? Comment mein likho.

TTL bada karne se problem sirf postpone hoti hai, khatam nahi hoti. Pause kitna bhi lamba ho sakta hai. Sahi fix hai fencing token. Idea yeh hai: lock service har lock ke saath ek number deta hai jo hamesha badhta rehta hai. Jaise A ko token 33 mila, aur baad mein B ko token 34. Ab client jab storage mein write karta hai, toh woh apna token bhi saath bhejta hai. Storage ka kaam hai ki jo sabse bada token usne dekha hai, usse chhote token wali write reject kare. Toh B ne token 34 ke saath write kiya. Jab A resume hota hai aur token 33 ke saath write bhejta hai, storage dekhta hai ki 33, 34 se chhota hai, aur reject kar deta hai. Lock ab sach mein safe hai, kyunki safety lock service par nahi, resource ke upar hai.

Ab sawaal: Redis fencing token deta hai? Seedha jawab: nahi, Redis ka SET NX lock apne aap koi increasing token nahi deta. Aap ek counter alag se INCR se bana sakte ho, lekin failover ke time woh bhi safe nahi hota. ZooKeeper aur etcd yahan alag hain. ZooKeeper mein lock ek znode hota hai, aur uska version number ya transaction id, jise zxid kehte hain, naturally badhta rehta hai, toh woh fencing token ban sakta hai. etcd mein bhi revision number yahi kaam karta hai. Isliye jab correctness sach mein critical ho, toh ZooKeeper ya etcd jaise consensus systems ko prefer kiya jaata hai.

Failure number 2: Redis failover. Maan lo aap ek Redis master aur replica use kar rahe ho. Client ne master pe lock liya. Replication asynchronous hai, toh woh lock abhi replica tak pahuncha nahi, aur master crash ho gaya. Replica promote ho gaya, aur usme woh lock hai hi nahi. Ab client B usi lock ko easily le leta hai, aur A aur B dono ke paas lock hai.

Redlock isi problem ke liye bana tha. Idea: 5 independent Redis masters, koi replication nahi. Client lock ke liye saare 5 ko try karta hai, aur agar kam se kam 3 mein, yaani majority mein, lock mil gaya aur total time TTL se kam laga, toh lock valid hai. Ek master fail ho bhi jaaye toh lock bacha rehta hai.

Lekin Kleppmann ne Redlock pe do sawaal uthaye. Pehla: Redlock timing assumptions pe depend karta hai, jaise clocks theek chal rahi hain aur pauses bounded hain. Distributed systems mein yeh assumptions sach nahi hote. Doosra aur zyada fundamental: Redlock koi fencing token nahi deta, toh GC pause wali problem wahi rehti hai. Redis ke creator antirez ne jawab diya ki pause wali problem sirf Redlock ki nahi, har lock service ki hai, aur fencing chahiye toh alag se layer kiya ja sakta hai. Dono ke points valid hain, aur interview mein yeh debate jaanna ek strong signal hai.

Ab Kleppmann ka sabse kaam ka point, jo aapko interview mein bolna chahiye: lock do wajah se liya jaata hai. Pehli wajah efficiency: kaam do baar na ho, jaise ek expensive report do baar generate na ho. Yahan agar kabhi kabhi lock fail ho jaaye toh sirf thoda cost hota hai, toh simple single Redis lock bilkul theek hai, Redlock ki complexity ki zaroorat nahi. Doosri wajah correctness: do clients ek saath kaam karenge toh data corrupt hoga, jaise paisa ya seat. Yahan sirf lock pe bharosa mat karo.

Aur ab asli interview answer, jo Tatkal wale video se connect karta hai. Correctness ke liye lock ke upar resource ko khud guard karna chahiye. Hum Tatkal mein dekh chuke hain: Redis ka lock ya counter sirf user experience ke liye hai, taaki zyada log fail hone ke liye payment tak na pahunchein. Lekin asli guard PostgreSQL mein conditional update hai: UPDATE seats SET status equals booked, version equals version plus 1 WHERE id match kare AND status available AND version match kare. Yeh version column ek fencing token ki tarah kaam karta hai. Purana client jo late resume hota hai, uska version stale hai, aur update zero rows pe fail ho jaata hai. Matlab Redis lock down ho, expire ho, ya duplicate ho, tab bhi data corrupt nahi hota. Isko bolte hain defense in depth.

Ab level ke hisaab se expectation, meri understanding ke mutabiq. SDE 2 se expect hota hai ki aap SET NX PX se lock banayein, aur owner check ke saath release karein. SDE 3 se expect hota hai ki aap GC pause aur TTL expiry ka scenario khud batayein, fencing token explain karein, aur yeh bolein ki correctness ke liye resource ko hi guard karna chahiye, jaise database ka conditional update ya version check. Redlock ka debate jaanna extra credit hai.

Ek line mein yaad rakho: lock efficiency ke liye Redis se theek hai, correctness ke liye fencing token ya database ka version check zaroori hai.
