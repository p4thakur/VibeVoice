Interview mein question aata hai: 10,000 phones ka stock hai, 10 lakh users hain, aur sale exactly 12:00:00 pe khulta hai. Aisa system design karo jisme ek bhi phone oversell na ho aur system down bhi na ho. Zyadatar candidates yahan Redis aur Lua bolke ruk jaate hain. Interviewer ke asli follow-up questions uske baad shuru hote hain. Is video mein hum wahi follow-ups dekhenge, aur 3 alag tareeke bhi, taaki aap sirf ek answer memorize na karo, balki trade off samjho.

Pehle numbers. 10 lakh users, 10,000 phones. Matlab 99 percent users ko phone milega hi nahi. Aur jo 10,000 orders actually commit hote hain, woh agar ek minute mein spread ho jaayein, toh sirf 170 orders per second ke aas paas hai, jo koi bhi database sambhal leta hai. Matlab asli problem order throughput nahi hai. Asli problem 10 lakh requests ka pehle second mein aana hai. System ka kaam hai un 9 lakh 90 hazaar losers ko jaldi se aur cheaply reject karna.

Pehla layer, edge pe. Sale ka page CDN se serve hota hai, static, database tak jaata hi nahi. Sale start ka time server se signed aata hai, aur client countdown chalata hai. Isse log page refresh karke server ko hammer nahi karte. Buy button 12:00:00 ke baad hi ek short lived token ke saath enable hota hai. Saath mein API Gateway pe rate limiting, per user aur per device, jiska poora video next week aa raha hai.

Doosra layer, Redis gate. Sale se pehle stock Redis mein pre load kar do, jaise key stock colon phone ke saath 10,000. Ab ek Lua script chalti hai, aur woh teen kaam ek atomic step mein karti hai. Pehla: check karo ki yeh user pehle se buyers set mein toh nahi, kyunki limit 1 phone per user hai. Doosra: check karo ki stock zero se zyada hai. Teesra: stock ko decrement karo aur user ko set mein add karo. Redis single threaded hai, toh yeh teeno steps beech mein interrupt nahi ho sakte. Ek Redis instance 1 lakh ke aas paas operations per second handle karta hai, toh 10 lakh requests kuch seconds mein filter ho jaati hain. Jo pass hue, unhe order reference milta hai.

Teesra layer, order pipeline. Jo 10,000 winners hain, unke orders Kafka ya SQS queue mein jaate hain. Ek worker order ko PostgreSQL mein PENDING status ke saath insert karta hai, aur inventory table pe conditional update chalata hai: UPDATE inventory SET stock equals stock minus 1 WHERE sku match kare AND stock greater than 0. Yeh database ka final guard hai. User ko screen pe order processing dikhta hai, aur result SSE ya polling se push hota hai. Phir 10 minute ka payment window, aur expire hone par stock wapas release, wahi delay queue wala pattern jo hum Tatkal video mein dekh chuke hain.

Ab interviewer ke follow-ups. Pehla: Redis aur database do jagah stock hai, toh agar crash ho jaaye toh? Yahan sabse zyada log fail hote hain. Maan lo Redis ne stock decrement kiya, aur worker order insert karne se pehle crash ho gaya. Ab Redis kehta hai 9,999 bache, database kehta hai 10,000. Isko undersell kehte hain, aur yeh oversell se kaafi cheap hai, kyunki ek phone sell nahi hua, jise baad mein reconcile kiya ja sakta hai. Rule yeh hai: Redis ko hamesha thoda strict ya barabar rakho, kabhi database se zyada generous mat rakho, aur sale ke baad Redis counter ko database se reconcile karo. Aur database ka conditional update hamesha final truth hai. Agar kisi order ka update zero rows pe fail ho, toh order cancel karo, user ko apology aur refund do. Monitoring mein alert lagao agar database stock kabhi negative jaaye, kyunki woh bug ka signal hai.

Yahan ek real world data point hai, jo senior level pe kaam aata hai. Shopify ne apni inventory reservations ko Redis counters se MySQL mein shift kiya, aur wajah yeh batayi gayi ki Redis aur MySQL do alag stores hain, aur unke beech koi single transaction possible nahi. Crash ke time counter aur ledger alag ho jaate the. Isse lesson milta hai: do jagah truth rakhna hamesha reconcile ka kaam badhata hai. Interview mein yeh bolna ki aap yeh trade off jaante ho, bahut strong signal hai.

Doosra follow-up: Redis bilkul nahi use karna chahte, toh? Option 1: PostgreSQL mein ek row per sellable unit rakho, yaani 10,000 rows, har phone ka ek row, status FREE ya RESERVED. Ab booking aise claim hoti hai: SELECT id FROM units WHERE sku match kare AND status FREE, LIMIT 1, FOR UPDATE SKIP LOCKED. SKIP LOCKED ka matlab hai ki jo row doosre transaction ne lock kar rakhi hai, use skip karo aur agli free row pick karo. Isse hot row ki problem khatam, kyunki har buyer alag row pe lock leta hai. Phir us row ka status RESERVED karo. Yeh design contention hata deta hai, lekin 10 lakh requests ko phir bhi database tak jaane se pehle filter karna padega, isliye edge aur rate limiting zaroori rehte hain.

Option 2: Kafka ke saath. Orders ko SKU ke hisaab se partition karo, matlab ek phone ki saari requests ek hi partition mein jaati hain, aur us partition ko ek hi consumer padhta hai. Ek hi writer hai toh locks ki zaroorat hi nahi, aur order naturally first come first served mein process hota hai. Trade off: ek partition ka throughput limited hai aur latency thodi badh jaati hai, lekin 10,000 stock ke liye yeh kaafi hai. Isko single writer principle kehte hain, aur interview mein yeh naam bolna ek achha signal hai.

Teesra follow-up: user ne double click kar diya ya network retry hua, toh? Wahi idempotency key. Client har buy attempt pe UUID bhejta hai, aur server database ke UNIQUE constraint se duplicate catch karta hai. Pichhle video mein hum yeh detail mein dekh chuke hain.

Chautha follow-up: bots. Sale ke pehle 50 milliseconds mein bots stock khatam kar dete hain. Fix: per user, per device aur per IP rate limiting, login ke baad hi buy token, aur OTP ya captcha jaisa ek extra step, jisse har attempt ka cost badh jaata hai.

Ab level ke hisaab se expectation, meri understanding ke mutabiq. SDE 2 se expect hota hai ki aap database ke conditional update se oversell rokein, aur samjhayein ki sirf database kyun nahi chalega. SDE 3 se expect hota hai ki aap Redis Lua gate, order queue, aur Redis aur database ke beech divergence ka plan khud bolein, aur batayein ki undersell oversell se behtar kyun hai. Alternatives, jaise SKIP LOCKED aur single partition writer, bolna extra credit hai.

Ek line mein yaad rakho: losers ko edge pe reject karo, winners ko Redis se filter karo, database ko final truth rakho, aur do jagah truth hone ka cost samjho.
