Here's an interview question. You have 10,000 phones in stock, 1,000,000 users, and the sale opens at exactly 12:00:00. Design a system where not a single phone is oversold, and the system doesn't go down. Most candidates say "Redis and Lua" and stop. The interviewer's real follow-up questions start after that. In this video we'll cover those follow-ups, and 3 different approaches, so you don't just memorize one answer.

First, the numbers. 1,000,000 users, 10,000 phones. That means 99 percent of users will never get a phone. And the 10,000 orders that actually commit, if they spread over a minute, come to only about 170 orders per second, which any database can handle. So the real problem isn't order throughput. The real problem is 1,000,000 requests arriving in the first second. The system's job is to reject the 990,000 losers quickly and cheaply.

Layer one, at the edge. The sale page is served from a CDN, static, and never touches the database. The sale start time comes signed from the server, and the client runs a countdown. That way people don't hammer the server with refreshes. The Buy button is enabled at 12:00:00 along with a short-lived token. On top of that, put rate limiting at the API Gateway, per user and per device. That's a full video of its own, coming next week.

Layer two, the Redis gate. Before the sale, preload the stock into Redis, for example a key called stock for the phone, set to 10,000. Now a Lua script runs, and it does three things in one atomic step. First, check whether this user is already in the buyers set, because the limit is 1 phone per user. Second, check that the stock is greater than zero. Third, decrement the stock and add the user to the set. Redis is single-threaded, so these three steps can't be interrupted in the middle. One Redis instance handles around 100,000 operations per second, so 1,000,000 requests get filtered in a few seconds. The ones who pass get an order reference.

Layer three, the order pipeline. The 10,000 winners' orders go to a Kafka or SQS queue. A worker inserts the order into PostgreSQL with status PENDING, and runs a conditional update on the inventory table: UPDATE inventory SET stock equals stock minus 1 WHERE the sku matches AND stock is greater than 0. That is the database's final guard. The user sees order processing on screen, and the result is pushed by SSE or polling. Then there's a 10-minute payment window, and on expiry the stock is released again, the same delay queue pattern we saw in the Tatkal video.

Now the interviewer's follow-ups. First: stock lives in two places, Redis and the database, so what if something crashes? This is where most people slip. Say Redis decremented the stock, and the worker crashed before inserting the order. Now Redis says 9,999 left and the database says 10,000. This is called undersell, and it's far cheaper than oversell, because one phone simply didn't sell, and you can reconcile it later. The rule is: always keep Redis equal to or stricter than the database, never more generous, and reconcile the Redis counter against the database after the sale. And the database's conditional update is always the final truth. If an order's update fails with zero rows, cancel the order, send the user an apology and a refund. In monitoring, set an alert if database stock ever goes negative, because that's the signal of a bug.

Here's a real-world data point that helps at senior level. Shopify moved its inventory reservations from Redis counters to MySQL, and the reason shared publicly was that Redis and MySQL are two separate stores, and there's no single transaction across them. At crash time, the counter and the ledger drifted apart. The lesson: keeping the truth in two places always adds reconciliation work. Saying in an interview that you know this trade-off is a very strong signal.

Second follow-up: what if you don't want to use Redis at all? Option one: keep one row per sellable unit in PostgreSQL, so 10,000 rows, one row per phone, with status FREE or RESERVED. A booking claims a row like this: SELECT id FROM units WHERE the sku matches AND status is FREE, LIMIT 1, FOR UPDATE SKIP LOCKED. SKIP LOCKED means: if another transaction has locked a row, skip it and pick the next free one. That removes the hot row problem, because every buyer locks a different row. Then set that row's status to RESERVED. This design removes contention, but the 1,000,000 requests still need to be filtered before they reach the database, so the edge and rate limiting remain necessary.

Option two: Kafka. Partition the orders by SKU, so all requests for one phone go to one partition, and exactly one consumer reads that partition. With a single writer, you don't need locks at all, and orders are naturally processed first come, first served. The trade-off: one partition's throughput is limited and latency goes up a little, but for 10,000 units that's enough. This is called the single writer principle, and saying the name in an interview is a good signal.

Third follow-up: the user double-clicked, or a network retry happened. The same idempotency key. The client sends a UUID with every buy attempt, and the server catches duplicates with a database UNIQUE constraint. We covered this in detail in the last video.

Fourth follow-up: bots. In the first 50 milliseconds of a sale, bots can drain the stock. The fix is rate limiting per user, per device and per IP, a buy token only after login, and an extra step like an OTP or captcha, so every attempt costs more.

Now the expectation at each level, based on my understanding. At SDE 2 you're expected to prevent oversell with a database conditional update, and explain why the database alone won't hold up. At SDE 3 you're expected to bring up the Redis Lua gate, the order queue, and a plan for Redis and the database diverging, and explain why undersell is better than oversell. Alternatives like SKIP LOCKED and a single-partition writer are extra credit.

In one line: reject the losers at the edge, filter the winners with Redis, keep the database as the final truth, and understand the cost of having truth in two places.
