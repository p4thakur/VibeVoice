Instagram once had a problem they nicknamed after Justin Bieber. Their system for spreading data evenly across hundreds of servers worked beautifully, and yet one single server would melt down while its neighbors sat nearly idle. The culprit was one wildly popular account. It's called the hot key problem, and it exposes a gap in consistent hashing that catches even experienced engineers off guard.

First, the setup, because it's the thing that was supposed to prevent this. To spread data across many cache servers, you use consistent hashing: you hash each key, a user ID, a photo ID, and that decides which server holds it. Hashing scatters keys evenly, so if you have a billion keys and a hundred servers, each server gets about one percent of the keys. Beautifully balanced. Problem solved, you'd think.

Here's the gap. Consistent hashing balances keys, not traffic. It makes sure each server holds roughly the same number of keys. It says nothing about how often each key is requested. And in the real world, requests are not spread evenly across keys at all, they're wildly lopsided. Most keys are requested rarely. A few are requested constantly. When Justin Bieber posts a photo, that one photo's key, which lives on exactly one server because that's what the hash decided, suddenly receives millions of requests in a few minutes. Every fan hitting that photo hashes to the same key, which maps to the same single server. That one server is now handling the traffic of millions, while the other ninety-nine servers, holding their perfectly-balanced share of boring keys, are nearly idle. The balanced design melts at one point.

This is a hot key: a single key so popular that the one server responsible for it becomes a bottleneck, a hotspot. And notice that adding more servers doesn't help at all. If you double your servers to two hundred, the Bieber key still hashes to exactly one of them. More machines, same single overloaded server. The usual scaling move is powerless here, because the problem isn't total capacity, it's that all the heat lands on one spot.

So how do you actually fix it? There are a few techniques, and they share one idea: break the one-key-one-server link for the hot keys. The first is replication of the hot key: instead of storing the popular photo on one server, store copies of it on many servers, and spread the incoming requests across those copies. Now the millions of requests are shared, no single server drowns. The cost is that you're using more memory to hold duplicates, and you only want to do this for the few keys that are actually hot, which means you need to detect them. The second technique is a local cache in front: each web server keeps its own small copy of the very hottest items in its own memory, so most requests for the Bieber photo are answered right there and never even reach the shared cache server. Since the item is read-only and hugely popular, a tiny local cache absorbs a massive fraction of the load. The third is request coalescing: if a thousand requests for the same key arrive at a server at nearly the same moment and it's not in cache, don't fire a thousand identical lookups to the database, let one go and have the rest wait for that single answer, preventing a stampede.

A hundred servers, perfectly balanced by key count, and one of them on fire. The fix isn't more servers, it's recognizing that popularity, not data, is what needs spreading, and giving the few hottest items more than one home.
