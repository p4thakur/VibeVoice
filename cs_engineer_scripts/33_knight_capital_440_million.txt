In forty-five minutes, a trading firm lost about 460 million dollars because one of eight servers never got a code update, and a counter that should have said "stop" had been deleted seven years earlier. This is Knight Capital, and almost every mistake in it is one you can make on a normal web service.

First you need to know what the software did. Knight ran a system called SMARS, a smart order router. When a big order came in to buy, say, a million shares, SMARS didn't fire one giant order at the market. It sliced the parent order into small child orders, sent them to different exchanges, and watched the fills come back. And here's the critical part: it kept a running counter of how many shares had already been filled, so it knew when to stop. Parent order says a million, counter reaches a million, stop sending children. That counter is the whole safety mechanism. Hold onto it.

Now the setup for the disaster. On August 1st, 2012, the New York Stock Exchange launched a new program, and Knight wrote new code to take part. That code had to go on eight servers, and it was deployed by hand, one server at a time, starting a few days earlier. A technician copied it to seven servers. The eighth was missed. No automated deploy that either does all eight or fails loudly, and no second person checking. That's mistake one, and it's the one every team recognizes.

Mistake two is the one that turned a missed server into a catastrophe. The new code was switched on by a flag, a single setting in the system. But that exact flag had been used years before to turn on a different, older feature called Power Peg, a testing tool retired back in 2003. The old Power Peg code was never deleted. It was just sitting there, dormant, behind that flag. So when the new code reused the flag to mean "turn on the new program," it was fine on the seven updated servers. On the eighth, which still had the old wiring, flipping that flag woke up Power Peg instead.

And now the counter comes back. Remember the running total of filled shares, the thing that tells the router to stop? Back in 2005, that counting logic had been moved out of Power Peg to somewhere else in the system. Nobody deleted Power Peg, but they took away the one piece that let it know a job was done. So when Power Peg woke up on that eighth server, it started slicing and sending child orders, and it never saw the fills come back, because its counter was gone. It never knew it was finished. It just kept buying and selling, in a loop, as fast as the machine could send.

The market opened at 9:30. A small number of real parent orders, 212 of them, hit that server, and each one spawned an endless flood of children. In about 45 minutes, the system fired over 4 million executions across 154 stocks, moving more than 397 million shares, buying at the high and selling at the low, over and over. Knight ended the morning holding billions in stock it never meant to own: roughly 3.5 billion dollars long in one set of stocks, 3.15 billion short in another.

Then the famous final mistake. The engineers saw the alerts but didn't yet understand the cause, and they did the intuitive thing: they rolled back the new code, uninstalling it from the seven good servers. But the bug wasn't the new code. The bug was the old code waking up on the server that never got the new code. By removing the new code everywhere, they spread the broken behavior from one server to all eight. The intuitive fix poured fuel on the fire. (Note: this rollback detail is the widely-told engineering account, not something stated in the SEC order.)

The loss was about 460 million dollars, more than the firm had. Knight needed an emergency rescue within days and was sold inside a year.

So what does an engineer actually take from this, the part you can use when you're designing a deploy or answering for one in an interview. Feature flags must be additive: a flag turns new code on, and when you retire a feature you delete its code, you don't leave it dormant behind a switch someone will reuse. Never give an old flag a new meaning while the old code still exists. Deploys go to all nodes automatically and verify themselves, because a human copying to eight boxes will eventually copy to seven. Any system that acts on the world in a loop, sending orders, sending emails, sending anything, needs a hard limit and a kill switch that a human can hit in seconds, not minutes. And when something is already on fire, rolling back blind can make it worse. You need to know which way the bug points before you move.

One missed server. One reused flag. One counter deleted seven years too early. Forty-five minutes, and a company that no longer exists.
