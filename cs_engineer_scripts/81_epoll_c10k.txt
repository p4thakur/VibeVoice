Around the year 2000, a web server handling ten thousand connections at once was considered a near-impossible feat. It even had a name, the C10k problem, the challenge of ten thousand concurrent clients. Today a single server handles millions of connections without breaking a sweat. What changed wasn't the hardware getting a thousand times faster. It was a change in how a program waits, and the idea behind it is one every backend engineer should carry.

Start with the old way, which seems perfectly reasonable: one thread per connection. A client connects, you hand that connection its own thread, and that thread handles everything for that client, reading requests, sending responses. For a few hundred clients, fine. But picture ten thousand. Now you have ten thousand threads. Each thread needs its own chunk of memory for its stack, often a megabyte or so, so ten thousand threads is gigabytes of memory gone just to exist. Worse, the operating system has to keep switching the processor's attention between all these threads, and each switch, saving one thread's state and loading another's, costs time and thrashes the caches. With ten thousand threads, the machine spends more time switching between them than doing actual work. The one-thread-per-connection model collapses under its own overhead, and that was the wall everyone hit.

Now here's the key observation that unlocks the fix: at any given instant, almost all of those ten thousand connections are doing nothing. They're idle, waiting, the user is reading the page, or the network is in transit. Only a handful have data actually ready to process right now. So dedicating a whole thread to each connection is enormously wasteful, you've got ten thousand threads and maybe fifty of them have anything to do at this moment. The other 9,950 threads are just sitting there, consuming memory and switching overhead, to wait.

So instead of one thread per connection, you use one thread, or a few, running an event loop. The single thread's job is: ask the operating system "which of my ten thousand connections have something ready right now?", get back the short list of ready ones, handle exactly those, then ask again. One thread races around servicing only the connections that need attention, and because servicing each one is fast, it keeps all ten thousand feeling responsive with almost no idle overhead. No per-connection thread, no gigabytes of stacks, no storm of context switches.

But this depends entirely on that question, "which connections are ready?", being cheap to ask, and that's where the real breakthrough lives. The old system calls for asking, named select and poll, worked like this: you hand the OS the entire list of all ten thousand connections, and it checks every single one and tells you which are ready. That's the trap, you pay a cost proportional to the total number of connections every single time you ask, even though only a few are ready. Ten thousand connections means scanning ten thousand every loop, over and over. The asking itself became the bottleneck.

The fix, called epoll on Linux, flips it. Instead of handing over the full list each time, you register your connections with the kernel once, and the kernel keeps track of them. Then, when you ask "what's ready?", it hands you only the connections that actually have activity, and the cost of asking is proportional to the number of ready connections, not the total number you're watching. Watching ten thousand mostly-idle connections now costs about the same as watching ten, because you only ever pay for the active ones. That change, from "cost grows with total connections" to "cost grows with active connections," is what broke the C10k barrier and kept going to millions.

This is the engine inside the software you use every day. Nginx, Node.js, Redis, they're all built on an event loop over epoll or its equivalents on other systems. It's why a single Nginx process can hold tens of thousands of connections on a modest server. And notice the subtler half of why select lost: it failed not because event loops were wrong, but because the act of finding ready connections scaled with the total number you were watching. The winning move was making the common question, "who needs me now?", cost only as much as the answer, not as much as the whole population.

Ten thousand connections, nearly all idle, served smoothly by a single thread. Not by giving each one a worker, but by asking the kernel only for the few that are ready, in a way that stays cheap no matter how many are waiting.
