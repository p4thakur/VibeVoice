The man who invented one of programming's most basic features called it his billion-dollar mistake, and he was probably being modest. The feature is the null reference, the idea of a variable that points to nothing, and the crashes it has caused, the null pointer exceptions and segfaults, add up to the single most common category of software bug in history. Its inventor, Tony Hoare, added it in 1965 for one simple reason, and understanding both the reason and the regret teaches you something deep about designing so that mistakes become impossible, not just unlikely.

Start with what null is. In programming, a variable often holds a reference, a pointer to some object, a user, a file, a connection. Null is a special value meaning this reference points to nothing, it's empty, there's no object here. Hoare introduced it in a language called ALGOL W, and his reasoning, by his own account, was simply that it was easy to implement. You needed some way to represent a reference that wasn't set yet, and null was the obvious, cheap answer: a special nothing-value that any reference could hold. It seemed harmless and convenient.

Here's why it became a catastrophe, and the mechanism is precise. Once null exists, every reference of a given type can secretly be either a real object or nothing, and the two look the same to the code. So a function that expects a user object might actually receive null. And when the program then tries to use it, calling a method on it, reading a field, following the pointer, there's nothing there, and the program fails: a null pointer exception in managed languages, a segmentation fault and crash in lower-level ones. The deadly part is that nothing forces you to check for null first. The type system says "this is a user," so you write code assuming you have a user, and it compiles fine, and then at runtime, sometimes, it's null, and everything explodes. The mistake, forgetting to handle the nothing-case, is invisible until it crashes in production, often in a situation you didn't test.

Multiply that by every reference in every program ever written, and you get Hoare's billion-dollar estimate, which is surely far too low. Null pointer errors have crashed operating systems, taken down services, corrupted data, and consumed an incalculable amount of debugging time across the entire history of the field. The feature that was easy to add became the most reliable source of failure in software, because it quietly introduced the possibility of nothing into places the code assumed something, and left it to fallible humans to remember to check, everywhere, forever.

Now the deep insight, the reason this is more than a war story. The real flaw isn't null itself, it's that null made an invalid state representable and indistinguishable from a valid one. A reference typed as user could hold a non-user, nothing, and the type system didn't tell you, so you couldn't be forced to handle it. The fix that modern languages adopted is to make the nothing-case explicit in the type, so the compiler forces you to deal with it. Languages like Rust, Swift, Kotlin, Haskell, use what's often called an option or maybe type: a value is either definitely-present or explicitly-optional, and the two are different types. If something might be absent, its type says so, and the compiler will not let you use it without first handling the empty case. And if a type says the value is present, then it genuinely cannot be null, so you never have to defend against it. The possibility of the crash is removed at compile time, not left to runtime vigilance.

This is one of the most powerful principles in software design: make invalid states unrepresentable. Rather than allowing a bad state to exist and relying on every programmer to remember to check for it, structure your types so the bad state simply cannot be expressed. Hoare's null allowed the invalid state, nothing where something was expected, to hide inside a normal-looking value, which meant the only defense was human discipline applied everywhere without fail, and humans don't do anything everywhere without fail. The option type instead encodes the presence-or-absence into the type itself, turning a runtime landmine into a compile-time question you're forced to answer. The error can't slip through, because the language won't build until you've handled it.

And it extends far past null. Whenever you design a data structure, an API, a function signature, the question isn't only "what are the valid inputs," it's "can this shape even express an invalid state, and if so, can I redesign it so it can't?" A field that should never be empty, a combination of flags that should never co-occur, an ordering that must hold, if your types allow the bad version to exist, someone will eventually create it and something will break. The strongest code isn't the code that carefully checks for every bad case, it's the code where the bad case cannot be written down in the first place.

A feature added in 1965 because it was easy became the most expensive mistake in software, because it let nothing hide where something was expected, and trusted humans to always check. The modern answer isn't to check harder. It's to make the invalid state impossible to express, so the compiler catches what discipline never could.
