An Uber interviewer asks you: a restaurant owner wants to see, in real time, the total order value and the top 5 food items over the last 1 hour, the last 1 day, and the last 1 week. Sounds easy, right? Most candidates say: I'll just run a GROUP BY query on the orders table. And that is exactly where the interview starts to fall apart. In this video we'll build the answer failure by failure, so that at the end you have an answer that fits an SDE 2 or SDE 3 interview.

First, let's be clear about the scale. Say there are 500,000 restaurants and 20 million orders a day, so roughly 250 orders per second on average, and several times that at dinner peak. Each restaurant owner opens a dashboard and it refreshes every few seconds. So reads are far heavier than writes, and each read must be fast.

Failure number 1: the GROUP BY query. SELECT item_id, COUNT(*) FROM order_items WHERE restaurant_id equals X AND created_at is within the last 7 days, GROUP BY item_id, ORDER BY count DESC, LIMIT 5. With an index on restaurant and time this works for a small restaurant. But a big restaurant has hundreds of thousands of rows in a week, and thousands of owners refresh every few seconds. Your PostgreSQL is now running a huge aggregation again and again, over the same data, to produce almost the same answer. The database melts. The fix is simple in idea: don't compute on read, compute on write. Keep the answer ready.

Now pause. If you have to keep the answer ready, what exactly do you store? A single running total for the last hour? Write your idea in the comments.

Here's the problem with one running total. A window like the last hour keeps sliding. When a new order arrives you add it, but when an old order leaves the window, you have to subtract it. To subtract it, you need to know when it expired. So the trick is time buckets. Break time into small buckets, say one minute each. For every restaurant and every minute, keep the totals for that minute: total order value, and a count per item. The last hour is then just the sum of the latest 60 buckets. The window slides by itself, because old buckets simply fall out of the range, and you never subtract anything.

Where do you store these buckets? In Redis. For each restaurant and minute, one hash for the order value, and one sorted set for item counts. When an order arrives, ZINCRBY the item in that minute's sorted set and INCRBY the value. Set a TTL on each bucket so old ones disappear. To get the top 5 for the last hour, you merge the 60 sorted sets with ZUNIONSTORE into a temporary key and read the top 5 with ZREVRANGE. This is fast because each restaurant has a small number of items.

Failure number 2: the one-week window. If you use minute buckets, one week is 10,080 buckets per restaurant, and merging that on every refresh is too much. The fix is multi-resolution buckets. Keep minute buckets for the last hour, hour buckets for the last day, and day buckets for the last week. When you need the last week, you merge 7 day buckets plus a few hour buckets for today. A good interview line: the window edge is slightly approximate, and for a dashboard that's perfectly acceptable, but you should say it out loud.

Now, how do orders reach Redis? Not directly from the order service, because that couples your order flow with your metrics. The order service writes the order to PostgreSQL and publishes an event to Kafka. Partition the topic by restaurant_id. That gives you two things: all events of one restaurant arrive in order at one consumer, and no two consumers fight over the same counters. A stream processor, like Flink or a simple consumer service, reads events, updates Redis buckets, and also writes aggregates to an analytics store.

Failure number 3: duplicates. Kafka gives you at-least-once delivery. If the consumer crashes after updating Redis but before committing the offset, the event is replayed, and now an order is counted twice. The owner sees wrong numbers. Fix: deduplicate by order_id. Before updating, do SET order_id with NX and a TTL of a couple of hours in Redis. If it already exists, skip. For exact numbers, you can also make the update and the dedupe key one Lua script, so they are atomic.

Failure number 4: late and out-of-order events. A mobile app was offline, and the order arrives 5 minutes late. If you bucket by arrival time, it lands in the wrong minute. So bucket by event time, the time the order was actually placed, and allow a small lateness, like 10 minutes. After that, drop it from the real-time view; the batch layer will fix it.

That brings us to the batch layer. Redis is for freshness, not for truth. The truth is in the events. Write every event from Kafka into an analytical store like ClickHouse. If Redis loses data, or a bug corrupted the counters, you can rebuild the buckets from ClickHouse. ClickHouse also serves the long-range queries, like last month, which Redis shouldn't hold.

One more interview trap: global top-K. If the interviewer asks for the top 100 items across the whole platform, a single sorted set will be a hot key. The answer is: partition counters, compute local top-K per shard, then merge. And if exactness isn't needed, mention a Count-Min Sketch with a heap, which gives approximate counts in tiny memory. Saying this shows depth.

Now what is expected at each level. At SDE 2, you should reject the GROUP BY approach, propose pre-aggregation with time buckets, and use Kafka plus Redis. At SDE 3, you should bring up duplicates and event-time bucketing yourself, explain multi-resolution windows, and separate the real-time layer from the source of truth.

In one line to remember: don't compute on read; bucket by time, aggregate from a Kafka stream into Redis, and keep the events in ClickHouse as the truth.
