Uber ka interviewer aapse poochta hai: ek restaurant owner real time mein dekhna chahta hai ki last 1 hour, last 1 day aur last 1 week mein total order value kitni thi aur top 5 food items kaunse the. Easy lagta hai, hai na? Zyada tar candidates bolte hain: main orders table pe GROUP BY query chala dunga. Aur yahin se interview bigadna shuru hota hai. Is video mein hum is answer ko failure by failure build karenge, taaki end mein aapke paas SDE 2 ya SDE 3 interview ke layak answer ho.

Pehle scale clear kar lete hain. Maan lo 5 lakh restaurants hain aur roz 2 crore orders aate hain, matlab average roughly 250 orders per second, aur dinner peak mein usse kai guna zyada. Har restaurant owner dashboard kholta hai aur woh har kuch seconds mein refresh hota hai. Toh reads, writes se bahut zyada heavy hain, aur har read fast honi chahiye.

Failure number 1: GROUP BY query. SELECT item_id, COUNT star FROM order_items WHERE restaurant_id equals X AND created_at last 7 days mein ho, GROUP BY item_id, ORDER BY count DESC, LIMIT 5. Restaurant aur time pe index ho toh chhote restaurant ke liye chalega. Lekin bade restaurant ke ek hafte mein lakhon rows hote hain, aur hazaaron owners har kuch seconds mein refresh karte hain. Aapka PostgreSQL baar baar wahi huge aggregation chala raha hai, same data pe, almost same answer ke liye. Database melt ho jaata hai. Fix idea mein simple hai: read pe compute mat karo, write pe compute karo. Answer ready rakho.

Ab pause karo. Agar answer ready rakhna hai, toh exactly store kya karoge? Last hour ka ek single running total? Apna idea comment mein likho.

Ek running total ke saath problem yeh hai. Last hour jaisa window slide karta rehta hai. Naya order aaye toh add kar lete ho, lekin purana order window se bahar jaaye toh subtract karna padta hai. Subtract karne ke liye pata hona chahiye ki woh kab expire hua. Isliye trick hai time buckets. Time ko chhote buckets mein todo, jaise ek minute ka bucket. Har restaurant aur har minute ke liye us minute ka total rakho: total order value, aur har item ka count. Last hour matlab latest 60 buckets ka sum. Window apne aap slide ho jaata hai, kyunki purane buckets range se bahar ho jaate hain, aur aapko kabhi subtract nahi karna padta.

Yeh buckets kahan store karoge? Redis mein. Har restaurant aur minute ke liye ek hash order value ke liye, aur ek sorted set item counts ke liye. Order aaye toh us minute ke sorted set mein item ko ZINCRBY karo aur value ko INCRBY. Har bucket pe TTL lagao taaki purane buckets khud hat jaayein. Last hour ke top 5 ke liye 60 sorted sets ko ZUNIONSTORE se ek temporary key mein merge karo aur ZREVRANGE se top 5 padh lo. Yeh fast hai kyunki ek restaurant ke items kam hote hain.

Failure number 2: one week ka window. Minute buckets rakhoge toh ek hafta ek restaurant ke liye 10,080 buckets hai, aur har refresh pe itna merge karna bahut zyada hai. Fix hai multi-resolution buckets. Last hour ke liye minute buckets, last day ke liye hour buckets, aur last week ke liye day buckets. Last week chahiye toh 7 day buckets plus aaj ke kuch hour buckets merge karo. Interview ke liye ek achhi line: window ka edge thoda approximate hai, aur dashboard ke liye yeh bilkul theek hai, lekin yeh baat aap khud bolo.

Ab orders Redis tak kaise pahunchte hain? Order service se seedha nahi, kyunki phir aapka order flow aur metrics aapas mein couple ho jaate hain. Order service order ko PostgreSQL mein likhti hai aur Kafka pe ek event publish karti hai. Topic ko restaurant_id se partition karo. Isse do cheezein milti hain: ek restaurant ke saare events ek consumer ko order mein aate hain, aur do consumers ek hi counter ke liye fight nahi karte. Ek stream processor, jaise Flink ya ek simple consumer service, events padhta hai, Redis buckets update karta hai, aur aggregates ko ek analytics store mein bhi likhta hai.

Failure number 3: duplicates. Kafka at-least-once delivery deta hai. Consumer Redis update karke offset commit karne se pehle crash ho gaya, toh event replay hoga aur ek order do baar count ho jayega. Owner ko galat numbers dikhte hain. Fix: order_id se dedupe karo. Update se pehle Redis mein order_id ke saath SET NX karo, TTL kuch ghante ka. Agar pehle se exist karta hai toh skip. Exact numbers chahiye toh update aur dedupe key ko ek Lua script mein daal do, taaki atomic rahe.

Failure number 4: late aur out-of-order events. Mobile app offline thi, aur order 5 minute late aaya. Arrival time se bucket karoge toh woh galat minute mein girega. Isliye event time se bucket karo, yaani jab order actually place hua, aur thodi lateness allow karo, jaise 10 minute. Uske baad real-time view mein drop kar do; batch layer use theek kar degi.

Yahan se batch layer aati hai. Redis freshness ke liye hai, truth ke liye nahi. Truth events mein hai. Kafka ke har event ko ClickHouse jaise analytical store mein likho. Redis ka data chala jaye, ya bug se counters corrupt ho jayein, toh aap ClickHouse se buckets rebuild kar sakte ho. Long-range queries, jaise last month, bhi ClickHouse serve karta hai, jo Redis mein nahi rakhne chahiye.

Ek aur interview trap: global top-K. Interviewer poochhe ki poore platform ke top 100 items chahiye, toh ek single sorted set hot key ban jayega. Answer: counters ko partition karo, har shard pe local top-K nikalo, phir merge karo. Aur exact numbers zaroori nahi hain toh Count-Min Sketch ke saath heap mention karo, jo tiny memory mein approximate counts deta hai. Yeh bolna depth dikhata hai.

Ab level ke hisaab se expectation. SDE 2 se expect hota hai ki aap GROUP BY approach reject karo, time buckets ke saath pre-aggregation propose karo, aur Kafka plus Redis use karo. SDE 3 se expect hota hai ki duplicates aur event-time bucketing khud bring up karo, multi-resolution windows explain karo, aur real-time layer ko source of truth se alag rakho.

Ek line mein yaad rakho: read pe compute mat karo; time se bucket karo, Kafka stream se Redis mein aggregate karo, aur events ko ClickHouse mein truth ki tarah rakho.
