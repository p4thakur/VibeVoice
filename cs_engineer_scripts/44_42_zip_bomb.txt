There's a file on the internet that is 42 kilobytes, small enough to email, that will fill 4.5 petabytes if you try to open it. That's 4.5 million gigabytes, out of 42 kilobytes. It's called 42.zip, a zip bomb, and it's not magic. It's compression used as a weapon, and understanding it teaches you exactly how compression works and why decompressing a stranger's file is dangerous.

Start with why compression can shrink a file at all. A compressor like the one inside zip looks for repetition. If a file contains the same byte a million times in a row, the compressor doesn't store a million bytes. It stores, in effect, a short instruction: "the byte zero, repeated one million times." That instruction is a few bytes. So a long, boring, repetitive stretch of data compresses to almost nothing, while random data, which has no repetition to exploit, barely compresses at all. Compression is really just finding patterns and writing them down shorter.

Now build the bomb. Take a file that's just four and a bit gigabytes of the same byte, over and over. Because it's maximally repetitive, it compresses down to about four megabytes, a thousand-to-one shrink. That alone isn't the trick. The trick is nesting. You take sixteen copies of that compressed file and put them inside another zip. Then sixteen of those inside another. And you do this five layers deep.

Here's why that explodes. Each layer multiplies the size by sixteen, and there are several layers, and at the bottom sits that thousand-to-one compressed data. Sixteen, times sixteen, times sixteen, and so on, times the thousand-fold compression of the core, multiplies out to that petabyte-scale final size. The outer file stays tiny because every layer is itself compressed. You're not storing the data. You're storing a recipe that, when followed, tells the machine to make copies of copies of copies.

And now the attack. A naive program, an antivirus scanner, an email server, an upload handler, wants to look inside the file, so it decompresses it to scan the contents. It opens layer one, which tells it to write sixteen files. It opens each of those, each says write sixteen more. By the time it reaches the bottom it's trying to write 4.5 petabytes to disk or into memory. The machine runs out of space or memory and falls over. A 42-kilobyte file took down a server, not with a clever exploit, but by asking it to do an enormous, perfectly legal amount of work.

The modern versions are even nastier. In 2019, a researcher named David Fifield built zip bombs that don't even need nesting. By overlapping files cleverly inside the zip format, a single layer can expand by a ratio of tens of thousands to one, which slips past defenses that only check for the recursive, nested kind.

And this generalizes far beyond zip files. Any time you expand, decode, or decompress input that came from someone you don't trust, the output can be vastly larger than the input, and the ratio is the attacker's to choose. So you never decompress blindly: you set a hard limit on how many bytes you'll write, a limit on nesting depth, and stop the moment either is exceeded, treating the decompressed size as untrusted, because the small file in front of you is lying about how big it really is. The same shape, a tiny bit of input triggering a giant amount of work, is the regex-backtracking story and others in its family. Small input, huge cost, chosen by an attacker.

42 kilobytes in. 4.5 petabytes out. The file isn't big. It's a set of instructions for becoming big, and the only defense is to refuse to follow them all the way down.
