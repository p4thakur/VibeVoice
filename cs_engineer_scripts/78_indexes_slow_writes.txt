Adding an index to a slow database query can make it a thousand times faster. So why not put an index on every column, and make everything fast? Because every index you add to speed up reads makes every write slower and every row bigger, and the day you discover that is usually the day your inserts fall off a cliff. The tradeoff between read speed and write speed is one of the most fundamental in all of databases, and an index is where you meet it face to face.

Start with what an index actually is, because the cost comes straight from the mechanism. Without an index, finding rows that match a condition, say all users in a certain city, means the database reads every single row in the table and checks each one, a full table scan. For a billion rows that's brutal. An index fixes this by keeping a separate, sorted structure, usually a B-tree, that maps values to the rows that have them, so the database can jump straight to the matching rows in about four reads instead of scanning a billion. That's the thousand-fold speedup. An index is, in effect, a pre-sorted copy of one column, maintained on the side, pointing back to the real rows.

And right there, in the words "maintained on the side," is the cost. That index is a separate structure that has to be kept correct. So every time you insert a new row, the database doesn't just add the row to the table, it must also insert an entry into every index on that table, placing it in the right sorted position in each one. Every time you update an indexed column, it must move the entry within the index. Every time you delete a row, it must remove the entry from every index. So if a table has one index, each write does roughly double the work, the table plus the index. If it has five indexes, each insert is updating six structures: the table and all five indexes. Your writes get slower in direct proportion to how many indexes you've added.

There are two more costs beyond speed. Space: each index is extra data on disk, so five indexes can easily make your stored data several times larger than the raw table. And remember that B-tree insert problem, placing a new entry into its sorted spot can mean jumping to a random location in the index and, when a page fills up, splitting it, which is random I/O. So on a write-heavy table, a pile of indexes turns one clean append into many scattered updates, exactly the random-write pain that makes writes expensive.

So the real picture is a balance, and it's the thing to reason about out loud in a design discussion. Indexes make reads fast and writes slow. A table that's read constantly and written rarely, like a product catalog, wants generous indexing, the read speedup is huge and the write cost is paid seldom. A table that's written constantly and read in bulk, like an event or logging table, wants very few indexes, because every index is a tax on the thing it does most, inserting. The question is never "should I index," it's "which specific queries do I need to be fast, and what's the minimum set of indexes that makes those fast without over-taxing my writes."

The common mistakes follow from ignoring the tradeoff. People add an index for every column just in case, and then wonder why inserts crawl and the database is three times bigger than the data. Or they add several overlapping indexes that each cost writes but that the query planner mostly ignores. The discipline is to index deliberately: look at your actual slow queries, add the specific indexes that serve them, and treat each index as a real, ongoing cost on every write, not a free speed boost.

And it holds for anything you precompute to make reads fast: a sorted index, a materialized view, a denormalized copy, a cache, each one has to be kept up to date on every write, trading write-time work and storage for read-time speed. Free lookups don't exist; you're always paying somewhere, and the skill is choosing to pay where it hurts least.

An index can make a read a thousand times faster, and that's exactly why you can't have one on everything. Each one is a second book you must update every time the story changes. Index for the reads you truly need, and respect that every one of them is a bill your writes have to pay.
