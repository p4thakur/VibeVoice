You check your Linux server, and it says almost all your RAM is used. You panic, you've got gigabytes of memory and something's eating it. You go hunting for the memory hog, and you find nothing. Here's the twist: nothing is wrong. Linux is using your "spare" memory on purpose, to make everything faster, and understanding why teaches you something deep about the relationship between memory and disk, summed up in a line every sysadmin eventually learns: free memory is wasted memory.

Start with the setup. Reading from disk is thousands of times slower than reading from RAM. So here's a question the operating system faces constantly: you have gigabytes of RAM that the applications aren't currently using. What should the OS do with it? Leave it empty and "free"? Empty memory does nothing. It helps no one. It's a resource sitting idle. Linux's answer is: don't waste it, fill it with copies of things from disk, so that if anyone needs them again, they come from fast RAM instead of slow disk.

This is the page cache. Every time a file is read from disk, Linux keeps a copy of that data in otherwise-unused RAM. The first time you read a file, it comes slowly off the disk, and Linux stashes a copy in memory. The next time anything reads that same file, Linux serves it straight from RAM, hundreds of times faster, and the disk isn't touched at all. Over time, the OS fills all the spare memory with the most recently and frequently used file data. So on a busy server, memory naturally trends toward "fully used," not because anything is leaking, but because the OS is doing its job: turning idle RAM into a giant disk cache.

Now the part that causes the panic. The standard memory readout lumps this cache into "used" memory, because technically it is holding data. So you see 95 percent used and assume you're nearly out. But this cached memory is completely different from memory an application has claimed. It's instantly reclaimable. The moment an application actually needs more memory, the OS simply drops some of the cached file copies, they're just copies, the originals are safe on disk, and hands that memory straight to the application. The cache costs you nothing in availability. It's using the memory while no one else wants it, and giving it up the instant someone does.

This is exactly why modern Linux tools draw a distinction between "free" memory and "available" memory. Free is the memory sitting truly empty, which on a healthy, busy server should be small, because empty memory is wasted. Available is the number that actually matters: free memory plus all the cache that could be instantly reclaimed if needed. If you have 1 gigabyte free but 40 gigabytes of reclaimable cache, you effectively have 41 gigabytes available for a new program. The scary "95 percent used" is mostly cache, and your real headroom is fine. The rule of thumb that saves you: look at available, not free, and never be alarmed that cache has eaten your RAM, that's the system working correctly.

There's a practical payoff beyond not panicking. This cache is why the second run of a program, or the second read of a file, is so much faster than the first, the data's in memory now. It's why databases and systems like Kafka deliberately lean on the page cache instead of building their own, as we've seen, they let the OS keep hot data in RAM for free. And it's why benchmarking is tricky: your first measurement hits cold disk, later ones hit warm cache, and they can differ by orders of magnitude, so you have to be clear about which you're measuring.

Your RAM is full, and that's good news. The empty memory you were proud of was doing nothing. The "used" memory you feared is mostly a disk cache that makes everything faster and vanishes the moment you need it back. Free memory is wasted memory.
