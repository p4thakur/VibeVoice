In Postgres, a long-running report can read a million rows while, at the same moment, other users are updating those exact rows, and neither one waits for the other. The reader never blocks the writers, the writers never block the reader, and yet the report sees a perfectly consistent snapshot. The trick that makes this possible is called MVCC, multi-version concurrency control, and it quietly changed how databases handle the oldest problem in the field: many people touching the same data at once.

Start with the old way, and its pain. The classic approach to keeping data consistent under concurrency is locking. When you read a row, you lock it so nobody can change it underneath you; when you write, you lock it so nobody can read a half-done change. It's correct, but it's slow and full of contention. A long report holding read locks on thousands of rows would freeze every writer trying to touch them. Readers and writers are constantly fighting over the same locks. In a busy system, everyone spends their time waiting in line.

MVCC's insight is to never overwrite data in place, and therefore never need readers and writers to fight. Instead of changing a row, an update creates a new version of that row, and the old version stays put. So at any moment, a single logical row might have several physical versions on disk, each tagged with information about which transaction created it and which transaction, if any, deleted or superseded it. In Postgres these are hidden columns on every row: one marking the transaction that created this version, one marking the transaction that expired it.

Now the magic of reads. When a transaction starts, it effectively gets a snapshot, a consistent view of the database as it existed at that instant. When it reads a row, Postgres looks at the available versions and shows it the one that was valid as of its snapshot, ignoring newer versions created by transactions that started after it. So the long report sees the data frozen at the moment it began, even as writers busily create newer versions all around it. The report doesn't need to lock anything, because it's reading old versions nobody is modifying, the writers are off making brand-new versions. Readers and writers stop colliding because they're literally working on different copies. A writer creates version two while a reader calmly reads version one. This is why, in Postgres, reading never blocks writing and writing never blocks reading, the single property that makes it feel so smooth under load.

Nothing is free, and MVCC's cost is one you should recognize because it directly connects to how Postgres can get into trouble. All those old row versions pile up. Once a version is older than every active transaction's snapshot, nobody can ever see it again, it's dead, but it's still sitting on disk taking up space. So Postgres needs a cleanup process, called vacuum, that periodically walks through and reclaims the space from dead versions. If vacuum can't keep up, maybe because a very long-running transaction is holding an old snapshot and preventing cleanup, dead versions accumulate, tables bloat, and the database slows down. That bloat, and the related problem of transaction-ID wraparound, are the classic Postgres operational headaches, and they exist precisely because the thing that makes reads and writes not fight, keeping multiple versions, means someone has to clean up the old ones later. The upside and the downside are the same mechanism, once again.

A million-row report and a flood of updates, on the same rows, at the same time, neither waiting for the other. Not by taking turns, but by never overwriting anything, so everyone reads the version they're entitled to, and a janitor sweeps up the old ones afterward.
