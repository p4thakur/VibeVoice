Discord stores trillions of chat messages. To do it, they ran a database cluster of 177 machines, and it was in constant pain, until they rebuilt it and the same workload ran on just 72. Fewer than half the machines, and far fewer problems. The story of why 177 became 72 is one of the best real-world lessons in computing: sometimes the thing slowing down your database isn't the database at all, it's the machinery running underneath it.

Start with where they were. Discord stored its messages in Cassandra, a well-regarded distributed database built for exactly this, huge volumes of writes spread across many nodes, which is why they chose it and why it served them for years. But as they grew to trillions of messages, Cassandra started hurting in specific, maddening ways. Latency became unpredictable: most requests were fast, but every so often one would stall badly, the tail-latency problem we've discussed, where the occasional slow response is what users actually feel. And the cluster was operationally painful, 177 nodes that needed constant babysitting, and certain hot partitions, very popular channels hammered by requests, that could overload individual nodes.

Now the deep cause of the latency, and this is the crux. Cassandra is written in Java, and Java programs run on top of a runtime that manages memory for you automatically, cleaning up unused objects in a process called garbage collection. The catch is that garbage collection periodically pauses the program to do its cleanup, these are GC pauses, and we met them back with Stack Overflow, where avoiding garbage was a speed strategy. For a database handling trillions of messages, those pauses were a recurring source of exactly the unpredictable stalls that hurt tail latency. The database logic itself was fine. But the runtime beneath it would freeze to collect garbage at unpredictable moments, and every request in flight during a pause just waited. The bottleneck wasn't Cassandra's design, it was the Java runtime it stood on.

So Discord moved to ScyllaDB. Here's the key: ScyllaDB is designed to be compatible with Cassandra, same data model, same core approach, but it's written in C++ instead of Java. And C++ has no garbage collector pausing things, memory is managed directly, so the single biggest source of unpredictable stalls simply disappears. On top of that, ScyllaDB uses an architecture called shard-per-core: it pins a slice of the data to each individual processor core, and that core alone handles its slice, with no locks and no coordination between cores, the same no-coordination, no-locking insight that makes single-threaded Redis fast, applied per core across a whole machine. And it manages its own memory cache directly rather than leaning on the runtime. The result was dramatically more efficient use of each machine, which is why the same workload that needed 177 Java-based Cassandra nodes fit on 72 C++-based ScyllaDB nodes, with far better and more consistent latency, and far less operational pain.

But they didn't stop at swapping the database, and this part is just as instructive. Remember the hot-partition problem, one wildly popular channel generating a storm of requests for the same data. Discord put a layer of their own in front of the database, written in Rust, whose job was request coalescing, the exact trick we saw for hot keys. When a flood of requests for the same message data arrives at nearly the same instant, instead of firing all of them at the database, this layer lets one request go through and makes the rest wait for that single answer, then hands the one result to all of them. So a viral channel that would have hammered the database with thousands of identical reads now sends essentially one, and the database barely notices. They fixed the hot-partition pain not inside the database but with a smart buffer in front of it.

Trillions of messages, 177 machines in constant pain, rebuilt onto 72 that run smoothly. Not by redesigning the database logic, but by replacing the runtime underneath it that kept freezing, and putting a clever buffer in front to absorb the hottest traffic. When it's slow and you can't find why, look down a layer.
