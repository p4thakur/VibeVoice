A single lost packet, one tiny piece of data dropped somewhere on the network, can freeze every image, script, and video loading on a web page, even the parts that already arrived perfectly. That maddening stall is called head-of-line blocking, and fixing it is why the newest version of the web's protocol, HTTP/3, made the radical move of abandoning TCP, the connection system the internet has run on for decades, and rebuilding on top of UDP instead.

Start with how a page loads today, and the improvement that accidentally created the problem. A web page needs dozens of files, images, stylesheets, scripts. The previous version, HTTP/2, made a big leap: instead of opening many separate connections, it sent all those files together over a single TCP connection, interleaved, in parallel streams. One connection, many files flowing at once. Faster and more efficient. So far so good.

But TCP has a rule baked into its DNA, and it's the rule that bites. TCP guarantees that data is delivered to the application in exactly the order it was sent, with nothing missing. It presents the connection as one perfectly ordered stream of bytes. To do that, if a packet goes missing, TCP holds back everything that arrives after it until the missing piece is re-sent and slotted into place, because it refuses to hand over byte 1,000 before byte 999. Here's the catch: TCP doesn't know about HTTP/2's separate streams. It just sees one long ordered line of bytes. So if one packet is lost, and it happened to carry a chunk of, say, one image, TCP holds back everything behind it, including data for completely unrelated streams, a script, a stylesheet, that arrived perfectly intact. They're all stuck in line behind the one missing piece, because TCP insists on delivering the whole stream in order. One lost packet for one file stalls every file. On a shaky connection, like a phone on a moving train, this happens constantly and makes everything feel broken.

HTTP/3's fix is to change the foundation so that streams are truly independent. Instead of TCP, it runs on a new transport protocol called QUIC, which is built on top of UDP. The crucial difference: QUIC understands streams natively. Each stream has its own ordering, tracked separately. So if a packet for one stream is lost, only that one stream waits for the retransmission, every other stream keeps flowing, unblocked. The lost chunk of one image no longer freezes the script and the stylesheet, because QUIC knows they're separate and doesn't make them wait on each other. The head-of-line blocking that TCP forced on all streams is gone, because the ordering guarantee is now per-stream instead of for the whole connection.

QUIC throws in more wins while it's at it. It has encryption built directly in, rather than bolted on as a separate layer, so it's secure by default. It establishes a connection in fewer round trips, and can even resume a previous connection with zero round trips of setup, making connections start faster. And it identifies a connection by an ID rather than by your network address, which means when your phone switches from Wi-Fi to cellular, changing its address, the connection survives the switch instead of dropping, something TCP can't do.

Now the question that puzzles people: why build on UDP, and not invent a brand-new protocol, or fix TCP itself? Two reasons. First, TCP's in-order-delivery behavior is implemented deep in the operating systems of every device and, crucially, in the routers and firewalls across the internet, so changing TCP itself would mean upgrading the entire world's infrastructure, impossible in practice. Second, the internet's routers and firewalls reliably pass only two kinds of traffic, TCP and UDP, anything genuinely new tends to get blocked along the way. UDP is the bare-bones option: it just sends packets with no ordering or reliability guarantees of its own. So QUIC takes UDP's blank slate and rebuilds reliability, ordering, and streams on top of it, in software that lives in the application and can be updated quickly, rather than in the operating system kernel and the network hardware that almost never change. They chose UDP precisely because it's the one flexible path that the existing internet will carry without interference.

QUIC started at Google and became an internet standard, with HTTP/3 following shortly after, in the early 2020s. And notice the two ideas it leaves you with. A guarantee can be a trap: TCP's strict total ordering, meant to help, became the exact thing that made unrelated data wait, and sometimes a weaker, more granular guarantee, order within each stream rather than across everything, is the one you actually want. And deploying something new in an old, vast system is as much about what the infrastructure will tolerate as about what's technically cleanest, which is why the future of web transport was built on humble UDP rather than something new from scratch.

One dropped packet, and the whole page freezes, even the parts that made it. The fix was to stop forcing unrelated data to wait in a single line, by leaving TCP behind and rebuilding the web on a protocol that keeps each stream in a line of its own.
