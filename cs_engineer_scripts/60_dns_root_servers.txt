The entire internet's naming system rests on just 13 special addresses, called the DNS root servers. Thirteen. It sounds absurdly fragile, like the whole internet could be toppled by taking out thirteen machines. But those 13 addresses are actually over a thousand physical servers, they're almost never even contacted, and the reason both of those things are true teaches you how hierarchy and caching make an impossibly large system manageable.

Start with the problem DNS solves. You type a name, like a website address, but computers connect using numeric IP addresses. Something has to translate the name into the number. That's DNS, the domain name system, the internet's phone book. But there's no single phone book, there are hundreds of millions of names, changing constantly. You can't put them all in one place. So DNS is organized as a hierarchy, a tree, and the root servers sit at the very top.

Here's how the hierarchy resolves a name, reading it right to left. Take a name ending in dot-com, dot-org, something. The root servers, at the top, don't know the address of any website. What they know is one level down: who is responsible for dot-com, who is responsible for dot-org, who handles each top-level ending. So the root points you to the dot-com servers. The dot-com servers don't know the final address either, but they know who's responsible for each name registered under dot-com, so they point you to that domain's own servers. And those servers, finally, know the actual address. It's a chain of delegations: each level doesn't hold the answer, it holds a pointer to the next level down that's one step closer. The root is just the starting point that knows where the top-level branches live.

Now, why only 13? The number comes from an old technical constraint. In the early design, the list of root servers had to fit inside a single, small network packet, the basic UDP response capped at 512 bytes. Thirteen server addresses was the most that reliably fit in that limited space. So the count, 13, which are named with the letters A through M, is a historical artifact of packet size, not a judgment that 13 machines is enough computing power. It's 13 addresses, not 13 computers.

And that distinction is the key to the fragility question, because each of those 13 addresses is served by many physical machines using anycast, the technique we've seen where the same address is announced from many places and routers send you to the nearest. So the 13 root addresses are actually spread across well over a thousand physical server instances scattered around the globe. Take out any one machine, or many, and the address keeps working from the others. The "13 machines" that sound so fragile are a thousand-plus machines wearing 13 addresses, specifically so that no small number of failures can hurt them.

There's a second reason the root is far more robust than it sounds: it's barely ever contacted, thanks to caching. Your computer and your internet provider's DNS servers remember answers they've already looked up. Once someone learns which servers handle dot-com, that fact is cached for a long time, days, because it rarely changes. So after the first lookup, essentially nobody needs to ask a root server who handles dot-com again for a long while. The root sits at the top of billions of lookups a day but is consulted only when a cache doesn't already know the next step, which is rarely. Caching absorbs the overwhelming majority of the load before it ever reaches the top of the tree. The most important servers in the world are among the least busy, by design.

Thirteen addresses holding up the whole internet, and yet almost unbreakable and almost idle. Not because thirteen machines are enough, but because each address is really a thousand machines, and caching means hardly anyone needs to climb all the way to the top.
