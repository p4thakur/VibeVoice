Most databases edit data in place. LSM trees never do. They only add. And the reason that's faster isn't an opinion, it's a hardware fact you can put a number on.

Start with the hardware, because the whole design falls out of it. A spinning disk has an arm that physically moves to a track. That move, a seek, takes around 10 milliseconds. So a disk can do only about a hundred random operations a second, each one landing somewhere different. But if you read or write one continuous stream, no seeking, it does 100 to 200 megabytes a second. Sit with that gap. Random: a hundred tiny operations a second. Sequential: hundreds of megabytes a second. That's a difference of a hundred to a thousand times, from the same disk, depending only on whether the arm has to jump around.

Now watch what a traditional database, a B-tree, does on a write. Your rows live in fixed pages on disk, kept sorted. To update one row, the database finds its page, reads it, changes the row, and writes the whole page back, to the same spot. If the next write is for a different key, that page is somewhere else entirely, so the arm seeks again. A write-heavy B-tree is a storm of random seeks. And it's worse than it looks: to change 100 bytes, you rewrite a whole page, maybe 8 kilobytes. That ratio, bytes written to disk versus bytes you actually changed, is called write amplification, and in a B-tree it's brutal because every small change drags a full page and a random seek with it.

The LSM tree, short for log-structured merge tree, refuses to seek. When a write comes in, it does two cheap things. It appends the change to a log on disk, one sequential write at the end of a file, purely so nothing is lost if the power dies. And it puts the change in a sorted structure in memory, called the memtable. Then it returns. Done. No page found, no page rewritten, no seek. The write is basically the speed of memory plus one sequential append.

When the memtable fills up, the database writes the whole thing to disk at once, in sorted order, as a brand new file called an SSTable, in one long sequential streak. And it never edits that file again. So how do you update a row? You don't. You write a newer version of the key into the current memtable, and it'll land in a newer SSTable. How do you delete? You write a little marker called a tombstone. The old value still sits in an older file; the system just knows the newest entry for a key wins.

That's the trick: every write, update, and delete has been turned into sequential appends. You've traded the disk's worst operation for its best one.

Nothing's free, and here's the bill, which is the part an interviewer wants to hear. First, reads get harder. To find a key, you check the memtable, then the SSTables from newest to oldest, because a newer file might override an older one. That could be many files. Two things rescue it. A Bloom filter on each file answers "is this key definitely not here?" in a few bits of memory, so you skip almost every file that can't have it. And a background job called compaction constantly merges small files into bigger sorted ones, throwing away overwritten values and tombstones, keeping the number of files small. Second, compaction itself rewrites data: the same row might be copied several times over its life as files merge upward. So the LSM has write amplification too, but it's all sequential, which is exactly the operation the disk is good at.

And that compaction is where the real war story lives. If writes arrive faster than compaction can merge, the files pile up, reads slow down as they check more and more files, and eventually the database deliberately throttles, or even stalls, incoming writes to let compaction catch up. Anyone who has run RocksDB or Cassandra hard has met a write stall: throughput falls off a cliff, not because the disk is full, but because the cleanup fell behind. The property that makes writes fast, defer the work and clean up later, is the same property that bites you when the cleanup can't keep up. Same mechanism, two faces.

The idea comes from a 1996 paper by Patrick O'Neil and colleagues, and Google's Bigtable made it famous. Today it's underneath Cassandra, RocksDB, LevelDB, HBase, and ScyllaDB, basically every database built to swallow writes.

So the thing to carry into a design discussion is this: a B-tree turns writes into random seeks and reads into a quick lookup; an LSM turns writes into sequential appends and makes reads do more work. If your workload is write-heavy, logging, metrics, event streams, you want the one that made writes sequential. If it's read-heavy with lots of range scans, the B-tree's in-place order may serve you better. You're not picking a faster database. You're picking which operation you want to be cheap.

Don't edit the past. Append the newest version, and clean up later, on the disk's own terms.
