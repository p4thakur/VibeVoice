Every program running on your computer right now believes it has the entire memory of the machine to itself, a vast private space starting at address zero. They're all wrong, and they're all wrong in the same way, at the same time, and somehow it all works perfectly. This beautiful shared illusion is called virtual memory, and it's one of the deepest and most load-bearing ideas in all of computing. Almost everything you rely on, process isolation, security, running more programs than you have RAM, is built on it.

Start with the problem it solves. Many programs run at once, and they all need memory. If every program used real, physical memory addresses directly, chaos follows. Two programs might both try to use address one million and stomp on each other's data. A buggy or malicious program could read or overwrite another program's memory, your banking app's secrets sitting exposed to any other process. And every program would have to be written knowing exactly which physical addresses were free, which is impossible when you don't know what else is running.

Virtual memory solves all of this with one move: give every program its own private, fake set of addresses, and put a translator in between. When a program uses what it thinks is address one million, that's a virtual address, a pretend one. Before it reaches the actual memory chips, a piece of hardware in the processor, the memory management unit, translates that virtual address into a real physical address, using a lookup table the operating system maintains for each program, called a page table. Memory is handled in chunks called pages, typically four kilobytes each, and the page table maps each of a program's virtual pages to some physical page in real RAM, wherever the OS decided to put it.

Now watch how much this one indirection buys you. First, isolation. Program A's virtual address one million and program B's virtual address one million translate to completely different physical locations, because each has its own page table. They literally cannot see each other's memory, because a program can only ever name virtual addresses, and its page table only maps to its own pages. A program has no way to even express "read that other program's memory." That's the foundation of all memory security on modern systems, enforced by the hardware on every single memory access.

Second, you can run programs that need more memory than you physically have. Because the mapping is in software's control, the OS can leave some of a program's pages on disk instead of in RAM, and only load them into physical memory when the program actually touches them. When a program accesses a virtual page that isn't currently in RAM, the hardware triggers a page fault, which hands control to the OS, which fetches that page from disk into memory, updates the table, and lets the program continue, unaware anything happened. This is swapping, and it's why you can open programs totaling more memory than your RAM, though if it happens too much, constant fetching from disk, called thrashing, everything crawls.

Third, a pile of powerful tricks fall out for free. The operating system can let two programs share a page by pointing both their page tables at the same physical page, that's how shared libraries live in memory once but serve many programs. It can map a file directly into a program's address space so reading the file is just reading memory. And it can implement the copy-on-write we saw with Redis's fork, let two processes share pages until one writes, then split just that page, all by manipulating these mappings and permissions. Every one of these is just a clever arrangement of the virtual-to-physical table.

Every program thinks it owns all of memory. None of them do. A hardware translator gives each one its own private map of a space that isn't really there, and from that single illusion comes isolation, security, and the ability to run far more than your RAM should allow. One layer of indirection, holding up the whole machine.
