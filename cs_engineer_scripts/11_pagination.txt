The "next page" button is one of the most common things in software, and the obvious way to build it gets catastrophically slow on exactly the pages that matter most. Page one is instant. Page ten thousand can take seconds, or time out. The reason is a database doing enormous amounts of invisible, wasted work, and the fix is a technique every backend engineer should have in their pocket.

Here's the obvious way, the one almost everyone writes first. To show page 10, with 20 results per page, you tell the database: skip the first 180 rows, then give me the next 20. In SQL that's OFFSET 180, LIMIT 20. It works perfectly in testing, because in testing you're always looking at page one or two. Then it ships, and someone asks for page 50,000.

Now watch what the database actually has to do for OFFSET one million. The word "skip" is a lie. The database cannot teleport to the millionth row. It has to generate the results in order, counting them off one by one, a million rows, and throw every single one of them away, just to arrive at the point where it starts keeping the 20 you asked for. So page one reads 20 rows. Page 50,000 reads a million rows and discards 999,980 of them. The deeper you page, the more work each page costs, and the cost grows in a straight line with how far in you are. The last page is the most expensive query in the whole system. Your pagination gets slower precisely as users go further, and bots that crawl every page hammer the slowest queries over and over.

The fix is to stop thinking in page numbers and start thinking "what came after the last thing I saw." It's called keyset pagination, or cursor pagination. Instead of asking for an offset, you remember the sorted value of the last row on the current page, say the last item's ID or timestamp, and the next page asks: give me 20 rows where the ID is greater than that last value. In SQL, WHERE id greater than the last id you saw, ordered, LIMIT 20.

Why is that fast? Because the column you're sorting and filtering on, the ID, almost always has an index, and an index is a sorted structure, a B-tree, that the database can jump into directly. "Find where ID is greater than this value" is a direct descent into the index to the right spot, in about four steps, no matter whether that spot is at the start or a million rows deep. Then you walk forward 20 entries. Page one and page fifty-thousand cost exactly the same: a quick seek plus 20 rows. You never count-and-discard anything, because you told the database precisely where to start instead of making it find the start by counting.

Nothing is free, and the tradeoff is the reason offset still exists. With cursors, you can't jump straight to "page 500," because you don't have the cursor for it, you only know where you are relative to what you've already seen. So cursor pagination gives you fast "next" and "previous" and infinite scroll, but not arbitrary numbered page links. It also needs a stable, unique sort key to anchor on, often you sort by timestamp and break ties with a unique ID, so two rows with the same timestamp can't confuse the boundary. For feeds, timelines, infinite scroll, and any big API, this is exactly the right trade, which is why essentially every large API, Stripe, GitHub, Twitter, paginates with cursors, not page numbers.

Page one, 20 rows. Page fifty-thousand the naive way, a million rows thrown in the bin. Page fifty-thousand the right way, 20 rows again. Stop counting from the start, and start from where you left off.
