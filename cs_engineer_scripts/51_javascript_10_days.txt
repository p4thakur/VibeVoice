The most widely used programming language on Earth, the one that runs every website you visit, was designed in ten days. Not ten months. Ten days, in May 1995, by one person under intense deadline pressure. That language is JavaScript, and nearly every strange, infamous quirk that programmers complain about, the ones that make "wat" a famous talk, traces directly back to the impossible speed and the political constraints of its birth. It's the ultimate lesson in how early decisions, made in a rush, echo forever.

Start with the circumstances, because they explain everything that followed. In 1995, the web was new, and Netscape, the dominant browser maker, wanted a scripting language inside the browser so web pages could do more than sit there. They hired Brendan Eich and gave him about ten days to produce a working prototype. Ten days to design and implement a programming language. On top of the absurd timeline came a political mandate: Java was the hot language of the moment, and management wanted this new language to look like Java, to ride its popularity, even though Eich's instincts drew from very different, more flexible language traditions. So he had to graft a Java-like surface onto very un-Java-like foundations, in a week and a half, and ship it.

The consequences are the quirks every JavaScript developer knows and curses. Because there was no time to design a careful type system, JavaScript does aggressive, surprising automatic type conversions, called coercion. Add a number and a string and it silently turns the number into text and glues them together. Compare things of different types and it quietly converts them with rules so tangled that the language ended up needing two different equality operators, a loose one that coerces and a strict one that doesn't, precisely because the original loose comparison behaves so unpredictably that experts tell you to avoid it. The infamous results, where adding and comparing various combinations of empty arrays, objects, and numbers produce baffling outputs, are all downstream of those hasty coercion rules. There was no time to make them principled, so they were made to just do something, and that something is now permanent.

And permanent is the key word, which is the deep part. Why weren't these obvious warts simply fixed later, once there was time? Because of a principle that governs the web above almost all others: don't break the web. Once millions, then billions, of web pages were written relying on JavaScript's exact behavior, quirks included, changing that behavior would break countless existing sites that people still use. The web has no central update, no way to fix all those pages. So the language is essentially frozen into backward compatibility with its earliest decisions. New features can be added on top, and modern JavaScript is far nicer to write, but the old quirks underneath cannot be removed, because something, somewhere, depends on each of them. The ten-day prototype didn't get a careful second draft, it got locked in by its own success.

This is path dependence: early choices constrain all later ones, and the more successful a system becomes, the more its initial decisions calcify, because more and more depends on them exactly as they are. JavaScript was a quick prototype that accidentally became the foundation of the entire web, and so a week and a half of rushed decisions in 1995 now shapes how billions of lines of code behave, every day, with no way back.

The language running the entire web was built in ten days, told to imitate Java, and never allowed to fix its birth defects because too much now depends on them. Every quirk is a fossil of that rushed week. What you ship fast can outlive you, so decide your foundations like they're forever, because sometimes they are.
