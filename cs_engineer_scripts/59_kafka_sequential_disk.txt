Kafka moves millions of messages a second by writing every one of them to disk, and it's faster than many systems that keep everything in memory. That sounds backwards. Disk is supposed to be the slow part. The resolution is a single idea that, once it clicks, changes how you think about storage forever: disk isn't slow, random access to disk is slow. Kafka is built, from the ground up, to never do the slow thing.

Start with the belief Kafka overturns. "Memory fast, disk slow" is a decent rule of thumb, but it hides a crucial distinction. A spinning disk has a physical arm that must move to a location before it can read or write. If you ask it to jump all over the place, reading a little here, writing a little there, it spends almost all its time moving the arm, and throughput collapses to a trickle. But if you ask it to read or write one long continuous stream, the arm stays put and the data flows at the disk's full speed. The gap between these two modes is enormous. A well-known analysis cited in Kafka's own documentation measured sequential access on a particular disk at around 600 megabytes per second, while random access on the same disk managed only a few hundred kilobytes per second, a difference of roughly six thousand times. Same disk. The only difference is whether you access it in order or all over the place.

Now the design that exploits it. A Kafka topic is, at heart, a log, an append-only sequence of messages. Kafka only ever writes by appending to the end of this log, and consumers read through it in order. It never updates a message in the middle, never hunts around to random spots. Every write is sequential, every read is a sequential scan from where a consumer left off. So Kafka uses the disk exclusively in its fast mode, the 600-megabytes-a-second mode, and never in its slow, arm-thrashing mode. It took the structure that fits the disk's strength, an ordered log, and refused to do anything else. This is the same insight behind LSM trees turning random writes into sequential appends, applied to an entire messaging system.

But Kafka has two more tricks, and they're why it beats in-memory systems. The first is that it leans on the operating system's page cache instead of managing its own. When Kafka writes to the log, the data first lands in the OS's file cache in RAM and is written to the physical disk in the background. And when consumers read recent messages, which is the common case, since they're usually keeping up and reading the newest data, those messages are still sitting in that RAM cache, so the read never touches the physical disk at all, it comes from memory. Kafka gets memory-speed reads for recent data for free, by trusting the OS cache, without building its own.

The second trick is zero-copy. Normally, to send a file from disk out over the network, the data gets copied several times through the computer's memory, from the cache into the application's memory, then into the network system's memory, wasting CPU and time on each copy. Kafka uses a system call, sendfile, that lets the operating system send the message data straight from the page cache to the network connection, skipping the trips through the application entirely. So a message flows from the log's cache directly to the consumer's network socket with almost no copying and almost no CPU involvement. Combined, these mean Kafka can pipe huge volumes of data from disk to many consumers while barely breaking a sweat.

Millions of messages a second, all written to disk, faster than memory-based rivals. Not by avoiding the disk, but by only ever using it the way it wants to be used, in one long, unbroken line.
