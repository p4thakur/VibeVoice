Redis can take a 20-gigabyte database in memory and save a perfect snapshot of it to disk, while still serving thousands of requests a second against that same data, without pausing, and without needing a second 20 gigabytes of RAM to do it. The trick it uses is one of the most elegant features in all of operating systems, called copy-on-write, and it's worth understanding because it's quietly running underneath far more than Redis.

Start with the problem. Redis keeps everything in memory for speed, but memory vanishes when the power goes out, so periodically it must write a snapshot of the whole dataset to disk. Here's the dilemma. The snapshot needs to be consistent, a clean picture of the data at one instant. But Redis is also busy handling live writes constantly. If it just started copying its memory to disk while writes kept changing that memory, the snapshot would be a smeared mess, half-old and half-new. The obvious fix, stop serving requests, freeze everything, copy it all to disk, then resume, would mean pausing the database for seconds on a big dataset. Unacceptable.

Redis's solution is to ask the operating system for a copy of itself, using a system call called fork. Fork creates a child process that is a duplicate of the parent. The child's job is simply to walk through the data and write it to disk, slowly, in the background, while the parent Redis keeps serving live traffic. The child has its own frozen view of the data as it was at the instant of the fork, so the snapshot it writes is perfectly consistent, even as the parent races ahead changing things.

But wait, doesn't duplicating a 20-gigabyte process mean instantly copying 20 gigabytes of memory, which would be slow and would need another 20 gigabytes free? This is where copy-on-write saves everything. When fork happens, the operating system does not actually copy the memory. Instead, it lets both the parent and the child share the exact same physical memory pages, and just marks all those pages as read-only and shared. The fork is nearly instant and uses almost no extra memory, because nothing was copied, the two processes are pointing at the same physical pages.

The copying only happens on write, which is the name. As long as both processes only read a shared page, they keep sharing it, free. But the moment the parent Redis modifies a page, say a write changes some data, the operating system catches that attempt to write to a read-only shared page, and only then makes a private copy of just that one page for the parent to modify, leaving the child's view, the old version, untouched. So the child continues to see the data exactly as it was at fork time, while the parent's changes land in fresh private copies. You only ever duplicate the specific pages that actually change during the snapshot, not the whole dataset. If little changes while the save runs, almost nothing gets copied. The 20-gigabyte snapshot might cost only a few megabytes of extra memory for the handful of pages touched during it.

Now the tradeoff, and it's a real operational gotcha. The extra memory used during a save is proportional to how much data gets written while the save is running. Normally that's small. But if your application happens to be doing a huge burst of writes right when the background save kicks off, many pages get copied, and in the worst case, if you rewrote everything during the save, you really could end up needing close to double the memory, briefly. This is a classic Redis surprise: a server with, say, 60 percent memory used suddenly runs out during a save, because a write spike collided with a snapshot and copy-on-write duplicated a large fraction of pages. The feature that usually costs almost nothing can, under a write storm, cost up to a full second copy of your data.

A 20-gigabyte snapshot, taken live, for the price of a few changed pages. Not by copying the data, but by sharing it and promising to copy only the parts that change, a promise the hardware itself enforces.
