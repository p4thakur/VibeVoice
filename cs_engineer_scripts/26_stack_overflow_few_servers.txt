Stack Overflow served over a billion page views a month from a handful of web servers. No fleet of hundreds. No microservices. Here's how.

By around 2016, one of the most visited sites for programmers ran its main website on roughly nine web servers. They weren't busy either. At peak, those machines sat at a low CPU load, around ten to fifteen percent. The company was famous for having a lot of room to spare.

To understand how, you have to do the one thing their engineers did obsessively: count. This is the exact habit that wins a system-design interview, so follow the arithmetic, because you can reuse every step of it.

Start with the load. On a single day in February 2016, the team published their own traffic. 209 million requests hit the load balancer, 66 million of which were real page loads. There are 86,400 seconds in a day, so divide: about 2,400 requests a second, and about 770 pages a second. That's the number everyone fixates on, and it's the wrong one. The number that decides how many servers you need isn't how many requests arrive, it's how much each one costs. Nine machines at ten percent means the cost per request was almost nothing. So where did it go?

Take the application code first. A question page rendered in about 23 milliseconds, 19 of them inside their own .NET code. Add up every millisecond of application time across the whole day and you get 447 hours. Divide by the 24 hours in that day: about 19 CPU cores, busy on average, for the entire site. Spread across nine servers, that's two cores of real work per machine. A modern server has far more than two cores. That is the empty CPU graph, explained. The work was simply never large.

Now the database, the part that takes most sites down. 504 million SQL queries that day. Divide 66 million page loads into that and you get about 7.6 queries per page. Not seventy, not seven hundred. Under eight small, indexed lookups to build a page. And the total time waiting on SQL all day was 168 hours, which across 504 million queries is 1.2 milliseconds each.

Here's the mechanism behind that 1.2 milliseconds, and it's the heart of the whole thing. Each database server had 384 gigabytes of RAM and was using about 365 of them. SQL Server keeps every page it reads in a buffer pool in memory, and the entire database, about two terabytes, lived on SSDs behind that. So a query for a popular question reads from RAM: no seek, no spinning disk, microseconds. And on the rare miss, an SSD answers in a fraction of a millisecond, not the ten milliseconds a hard drive would cost. They didn't beat the database problem with cleverness. They bought enough RAM to hold the working set, which is the single most important sentence you can say about scaling a read-heavy system in an interview.

Then, in front of the database, caching in layers, and the pattern here is the reusable one. Redis took 5.8 billion hits that day. Compare that to 504 million SQL queries: about eleven Redis reads for every one query that reached SQL. Redis held the counts, the vote tallies, the hot lists. And in front of Redis sat an even faster layer: each web server kept its own in-process cache, a plain dictionary inside the application's memory, read in nanoseconds with no network hop at all. Picture the shape: an in-memory dictionary catching most reads, Redis catching most of what's left, SQL's buffer pool catching most of that, and an SSD underneath for the rest. Each layer is roughly ten to a hundred times cheaper than the one below it, and each absorbs the traffic so the next barely feels it. That layering, not one magic cache but a gradient of them, is what you draw on the whiteboard when someone asks you to scale reads.

Two more choices made the per-request cost small. They kept the site as one large application instead of hundreds of services, so building a page didn't mean twenty network calls across a cluster, and every network hop you remove is latency and a failure you never pay for. And they treated slow code as a bug. They wrote their own tiny database mapper, Dapper, because the full object-relational library they'd used added reflection and allocated objects on every single query. Fewer allocations matters for a concrete reason: .NET's garbage collector pauses your threads when it runs, and the less garbage you make, the fewer pauses at the worst possible moment, under peak load.

None of this is free, and the tradeoff is the part an interviewer actually wants to hear. Scaling up means a few very expensive machines, and a single database server you've filled with 384 gigabytes of RAM can't simply be joined by a tenth node the way a sharded, scaled-out system can. Stack Overflow bought room to grow by giving each Stack Exchange site its own database, but that's a ceiling they chose, not one they escaped. And that ten percent CPU is deliberate headroom, reserved for traffic spikes, a bad deploy, a runaway query, an attack. They paid for idle on purpose.

This isn't an argument against the cloud or against scaling out. Some systems really do need thousands of machines. But many don't. Before you add servers, ask whether you've used the ones you have.

A well-tuned machine can do the work of ten that aren't.
