Interview ke sabse common questions mein se ek: rate limiter design karo. Almost har API wale design round mein yeh ya toh standalone question hota hai, ya aapko khud ek component ki tarah add karna padta hai. Zyadatar candidates token bucket bolte hain aur ruk jaate hain. Is video mein hum ek aisa rate limiter banayenge jo Tatkal ke 3 lakh users ke saamne bhi chale, aur 4 failures ke through dekhenge ki har galat design kahan break hota hai. Aur har step pe exact algorithm aur exact Redis command bhi.

Pehle clarifying questions, jo interview mein sabse pehle poochne chahiye. Limit kis pe lagani hai: user id, IP, API key? Hard limit hai ya burst allowed? Kya limit sirf ek service pe hai ya poore system pe? Aur jab limit cross ho, toh kya hona chahiye: request reject ho ya queue mein jaaye? Hum maan lete hain: per user aur per IP limit, thoda burst allowed, aur reject karna hai.

Failure number 1: har server ka apna counter. Sabse pehla design jo sabse pehle yaad aata hai: har app server apni memory mein counter rakhe. Lekin 10 servers hain aur load balancer requests spread kar raha hai, toh har user ko actually 10 guna limit mil jaati hai. Aur server restart hua toh counter reset. Matlab limit enforce hi nahi hui. Isliye counters ek shared store mein chahiye, aur yahan Redis aata hai: fast, in memory, aur ek instance 1 lakh ke aas paas operations per second handle kar leta hai.

Failure number 2: race condition. Ab counters Redis mein hain. Lekin candidate yeh likhta hai: GET count, agar limit se kam hai toh SET count plus 1. Yeh do alag commands hain. 2 requests ek saath aayi, dono ne count 99 dekha, dono ne allow kiya, aur limit 100 ki jagah 101 ho gayi. Isi tarah 3 lakh requests mein limit bahut zyada cross hogi. Fix: check aur update ek atomic step mein hone chahiye. Simple fixed window counter ke liye INCR command atomic hai, aur saath mein EXPIRE lagao. Lekin complex algorithms ke liye Lua script, kyunki Redis ek Lua script ko bina interrupt ke chalata hai.

Failure number 3: fixed window ka boundary burst. Fixed window counter simple hai: har minute ka ek counter, limit 100. Lekin ek user 12:00:59 pe 100 requests bhejta hai, aur 12:01:00 pe phir 100 bhejta hai. Do second mein 200 requests, aur kisi window ka rule break nahi hua. Matlab boundary pe 2 guna burst. Ab pause karo. Is problem ko fix karne ke liye aap kaunsa algorithm choose karoge? Comment mein likho.

Ab algorithms ka comparison, jo interview ka core hai. Sliding window log: har request ka timestamp Redis ke sorted set mein rakho, aur window ke bahar ke purane timestamps remove kar do. Accuracy perfect hai, lekin memory per user requests ke barabar lagti hai, jo scale pe expensive hai. Sliding window counter: do fixed windows ke counters rakho, pichli window aur current window. Estimate aise nikalte hain: pichli window ka count, multiplied by us window ka remaining fraction, plus current window ka count. Memory sirf 2 counters per user, aur accuracy kaafi achhi. Token bucket: har user ka ek bucket hai jisme capacity tokens hain, aur tokens ek fixed rate se refill hote hain. Har request ek token consume karti hai. Bucket empty ho toh reject. Burst allowed hai, capacity tak, aur average rate smooth rehta hai. Isliye zyadatar public APIs token bucket use karte hain. Leaky bucket output ko constant rate pe smooth karta hai, jo network traffic shaping ke liye better hai, API ke liye kam use hota hai.

Mera recommendation: Tatkal jaise user facing API ke liye token bucket, kyunki thoda burst chalta hai, aur memory O(1) hai. High volume internal APIs ke liye sliding window counter.

Ab implementation. Token bucket Redis mein ek hash ke roop mein store hota hai, jisme do fields hain: tokens aur last refill time. Ek Lua script chalti hai. Woh pehle bucket ka state padhti hai. Phir current time aur last refill time ka difference nikalti hai, aur utne tokens add karti hai jitne is beech refill hone chahiye the, capacity se zyada nahi. Phir agar tokens 1 ya usse zyada hain toh ek token deduct karti hai aur allow return karti hai, warna reject. Phir naya state wapas hash mein likhti hai, aur key pe EXPIRE lagati hai, taaki inactive users ki keys automatically delete ho jaayein. Yeh poora kaam ek atomic step hai, isliye race condition nahi.

Rejected request ke liye 429 Too Many Requests return karo, saath mein Retry After header, jisse client ko pata chale ki kab dobara try karna hai. Aur X RateLimit Remaining jaise headers bhi bhej sakte ho. Aur client side pe exponential backoff with jitter, taaki rate limited clients ek saath retry karke storm na banayein.

Failure number 4: Redis hi down ho gaya. Ab sawaal yeh hai: rate limiter fail ho gaya toh saari requests block karein ya sab allow karein? Yeh ek design decision hai, aur interview mein isse explicitly bolna chahiye. Normal API ke liye fail open: limiter down hai toh requests allow karo, kyunki availability zyada important hai. Lekin login, OTP ya payment jaise abuse sensitive endpoints ke liye fail closed ya ek strict local limit lagao. Aur Redis ka latency bhi ek cost hai, isliye har request pe 1 network hop. Local in memory limiter ko ek first line of defense rakh sakte ho, aur Redis ko global limit ke liye.

Aur ek aur follow up: multiple regions. Agar users 2 regions mein hain, toh global limit enforce karna hard hai, kyunki regions ke beech sync mein latency hai. Common approach: har region ko limit ka ek share do, jaise 100 requests ka 50 aur 50, aur thoda approximate rakho. Perfect global accuracy ki zaroorat usually hoti nahi.

Aur layers ka concept: limit sirf ek jagah nahi lagti. Per user, per IP, aur global system level, teeno alag. Global limit tab bhi kaam karta hai jab attacker bahut saare IPs use kare.

Ab level ke hisaab se expectation, meri understanding ke mutabiq. SDE 2 se expect hota hai ki aap token bucket ya sliding window explain karein, aur Redis mein shared counter rakhein. SDE 3 se expect hota hai ki aap race condition ko Lua se solve karein, algorithms ka trade off bolein, fail open aur fail closed ka decision explain karein, aur multi region ka plan khud propose karein.

Ek line mein yaad rakho: shared counter Redis mein, check aur update ek atomic Lua script mein, burst ke liye token bucket, aur Redis down hone par kya hoga woh pehle se decide karo.
