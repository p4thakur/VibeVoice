Design a Facebook-like news feed, where users post text, images and videos, and see a feed of the people they follow. This is one of the oldest and most repeated questions in system design interviews, which is exactly why interviewers expect more than a textbook answer, and why candidates still fail it. The interviewer is waiting for one particular word: the celebrity problem. In this video we'll build the design failure by failure, so you reach that point naturally.

First, the basic data. Users follow other users. A post belongs to one user. The feed of a user is the latest posts from everyone they follow. Say 500 million users, each following 200 people on average, and the feed is opened many times a day. So feed reads are enormously more frequent than posts, and the feed must open in well under a second.

Failure number 1: build the feed on read. This is called fan-out on read, or the pull model. When a user opens the app, you fetch the list of people they follow, fetch the latest posts of each of them, merge and sort by time, and return the top 20. In SQL, it's a JOIN between the follows table and the posts table, with ORDER BY time. For a user following 200 people, that's 200 lookups and a merge on every single open. Multiply by millions of users opening the app at the same time, and your database is burning. Reads are the common case, and you made them the expensive case.

Now pause. If reads are the common case, where should the work happen? At read time, or at post time? Write your answer in the comments.

The answer: do the work at post time. This is fan-out on write, the push model. When someone posts, you find all their followers and push the post ID into each follower's precomputed feed. Where is that feed stored? In Redis, as a list or sorted set per user, holding the latest few hundred post IDs. Now opening the feed is one Redis read: fetch the IDs, then fetch the post details in a batch, and you're done in a few milliseconds. We move the cost from the frequent operation to the rare one.

How does the push happen? Not inside the post request, because a user with 10,000 followers would wait while 10,000 writes happen. The post service saves the post to the database and publishes an event to Kafka. A group of fan-out workers consumes the event, reads the follower list, and writes the post ID into each follower's feed in Redis. The user gets a response immediately, and the feed update happens asynchronously. Mention that the feed is eventually consistent, and a delay of a second or two is fine.

Failure number 2: the celebrity problem. A user with 50 million followers posts a photo. Your fan-out workers now have to do 50 million Redis writes for one post. This takes minutes, it floods your Kafka pipeline, and it delays the posts of everyone else behind it. And most of those followers might not even open the app today. The push model collapses for high-follower accounts.

The fix is a hybrid. For normal users, use fan-out on write. For celebrities, don't fan out. Instead, when a user opens their feed, you take their precomputed feed from Redis, which has the normal people's posts, and then fetch the latest posts from the few celebrities they follow at read time, and merge the two. Since a user follows only a handful of celebrities, this extra read is small and cheap, and those celebrity posts can be cached heavily because millions of users read the same ones. The threshold, say a few hundred thousand followers, is a tunable. This hybrid is the answer the interviewer is waiting for.

Failure number 3: wasted work on inactive users. Even for normal users, pushing into the feeds of people who haven't logged in for months is wasteful. Optimization: only maintain precomputed feeds for recently active users. When an inactive user comes back, build their feed on demand with the pull method, once, and cache it.

Now the storage side. Posts themselves go into a database. A common choice is a wide-column store like Cassandra, or sharded PostgreSQL, keyed by post ID, because posts are written once and read by ID. The follow graph, who follows whom, needs fast lookup in both directions: who do I follow, and who follows me. Store it in a sharded database, with a cache in front for celebrity follower lists. Images and videos never go in the database. They go in object storage like S3, and are served through a CDN. The post only stores the media URL. The upload is done with a pre-signed URL so the file goes directly from the client to S3, not through your servers. Videos are transcoded into multiple resolutions by a background pipeline.

Failure number 4: likes and view counts on a viral post. A post gets a million likes in a minute. If every like does an UPDATE on the same row, that row becomes a hot spot, with lock contention, exactly like the hot row in the Tatkal video. The fix: write the like event to Kafka, and aggregate counts in Redis with INCR, and flush the totals to the database in batches every few seconds. The exact count shown to users can lag slightly. For the one-time rule that a user can like a post only once, keep a likes table with a unique constraint on user and post. The counter is an approximation for display, and the table is the truth.

Last piece, pagination. Never use OFFSET, because the feed changes while the user scrolls and they would see duplicates. Use cursor-based pagination, where the cursor is the ID or timestamp of the last post seen.

Now the expectations. At SDE 2, you should reject the join-on-read approach, propose fan-out on write with Redis and Kafka, and keep media in S3 with a CDN. At SDE 3, you should bring up the celebrity problem yourself and propose the hybrid, handle inactive users, deal with hot counters through async aggregation, and talk about cursor pagination and eventual consistency.
