Facebook jaisa news feed design karo, jahan users text, images aur videos post karte hain, aur apne follow kiye hue logon ka feed dekhte hain. Yeh system design interviews ke sabse purane aur sabse repeat hone wale questions mein se ek hai, aur isi wajah se interviewer textbook answer se zyada expect karta hai, aur candidates phir bhi fail ho jaate hain. Interviewer ek particular word ka wait kar raha hota hai: celebrity problem. Is video mein hum design ko failure by failure build karenge, taaki aap us point tak naturally pahunchein.

Pehle basic data. Users doosre users ko follow karte hain. Ek post ek user ki hoti hai. Kisi user ka feed woh latest posts hain jo woh jinhe follow karta hai unhone ki hain. Maan lo 50 crore users hain, har ek average 200 logon ko follow karta hai, aur feed din mein kai baar khulta hai. Toh feed reads, posts se bahut zyada frequent hain, aur feed ek second se kaafi kam mein khulna chahiye.

Failure number 1: feed ko read pe build karna. Isse fan-out on read ya pull model kehte hain. User app kholta hai, aap uske follow kiye hue logon ki list fetch karte ho, har ek ki latest posts fetch karte ho, time se merge aur sort karte ho, aur top 20 return karte ho. SQL mein yeh follows table aur posts table ka JOIN hai, ORDER BY time ke saath. 200 logon ko follow karne wale user ke liye har ek baar app kholne pe 200 lookups aur ek merge. Isse un lakhon users se multiply karo jo ek saath app khol rahe hain, aur aapka database jal jaata hai. Reads common case hain, aur aapne unhe expensive case bana diya.

Ab pause karo. Reads common case hain, toh kaam kahan hona chahiye? Read time pe, ya post time pe? Apna answer comment mein likho.

Answer: kaam post time pe karo. Yeh fan-out on write hai, push model. Jab koi post karta hai, aap uske saare followers dhundhte ho aur post ID ko har follower ke precomputed feed mein push kar dete ho. Woh feed kahan store hota hai? Redis mein, har user ke liye ek list ya sorted set, jisme latest kuch sau post IDs hote hain. Ab feed kholna ek Redis read hai: IDs fetch karo, phir post details batch mein fetch karo, aur kuch milliseconds mein kaam khatam. Humne cost frequent operation se hata ke rare operation pe daal di.

Push hota kaise hai? Post request ke andar nahi, kyunki 10,000 followers wale user ko 10,000 writes ke liye wait karna padega. Post service post ko database mein save karti hai aur Kafka pe ek event publish karti hai. Fan-out workers ka ek group event consume karta hai, follower list padhta hai, aur post ID ko har follower ke Redis feed mein likhta hai. User ko response turant mil jaata hai, aur feed update asynchronously hota hai. Yeh mention karo ki feed eventually consistent hai, aur ek-do second ka delay theek hai.

Failure number 2: celebrity problem. 5 crore followers wala user ek photo post karta hai. Aapke fan-out workers ko ek post ke liye 5 crore Redis writes karni hain. Isme minutes lagte hain, Kafka pipeline flood ho jaati hai, aur uske peeche ki baaki sab ki posts delay ho jaati hain. Aur un followers mein se zyada tar shayad aaj app kholenge bhi nahi. High-follower accounts ke liye push model collapse ho jaata hai.

Fix hai hybrid. Normal users ke liye fan-out on write. Celebrities ke liye fan-out mat karo. Uske bajaye, jab user feed kholta hai, Redis se uska precomputed feed lo, jisme normal logon ki posts hain, aur jin kuch celebrities ko woh follow karta hai unki latest posts read time pe fetch karo, aur dono ko merge karo. Kyunki user sirf kuch celebrities follow karta hai, yeh extra read chhota aur cheap hai, aur un celebrity posts ko heavily cache kar sakte ho kyunki million users wahi posts padhte hain. Threshold, jaise kuch lakh followers, ek tunable hai. Yeh hybrid hi woh answer hai jiska interviewer wait kar raha hai.

Failure number 3: inactive users pe wasted work. Normal users ke liye bhi, jo log mahino se login nahi hue unke feed mein push karna waste hai. Optimization: precomputed feeds sirf recently active users ke liye maintain karo. Inactive user wapas aaye toh pull method se ek baar on demand feed build karo aur cache kar do.

Ab storage side. Posts khud ek database mein jaati hain. Common choice Cassandra jaisa wide-column store, ya sharded PostgreSQL, post ID se keyed, kyunki posts ek baar likhi jaati hain aur ID se padhi jaati hain. Follow graph, yaani kaun kisko follow karta hai, ko dono directions mein fast lookup chahiye: main kisko follow karta hoon, aur mujhe kaun follow karta hai. Isse sharded database mein rakho, aur celebrity follower lists ke aage cache. Images aur videos kabhi database mein nahi jaate. Woh S3 jaise object storage mein jaate hain, aur CDN se serve hote hain. Post sirf media URL store karti hai. Upload pre-signed URL se hota hai, taaki file client se seedha S3 jaaye, aapke servers se hokar nahi. Videos ko background pipeline multiple resolutions mein transcode karti hai.

Failure number 4: viral post pe likes aur view counts. Ek post ko ek minute mein million likes mil jaate hain. Har like same row pe UPDATE kare, toh woh row hot spot ban jaati hai, lock contention ke saath, bilkul Tatkal video ki hot row jaisa. Fix: like event ko Kafka mein likho, Redis mein INCR se counts aggregate karo, aur totals ko har kuch seconds mein batches mein database mein flush karo. Users ko dikhne wala exact count thoda lag kar sakta hai. Ek user ek post ko sirf ek baar like kar sakta hai, yeh rule enforce karne ke liye likes table rakho jisme user aur post pe unique constraint ho. Counter display ke liye approximation hai, aur table truth hai.

Last piece, pagination. OFFSET kabhi use mat karo, kyunki user scroll karte time feed badalta rehta hai aur usse duplicates dikhenge. Cursor-based pagination use karo, jahan cursor last dekhi hui post ki ID ya timestamp hai.

Ab expectations. SDE 2 se expect hota hai ki aap join-on-read approach reject karo, Redis aur Kafka ke saath fan-out on write propose karo, aur media ko S3 aur CDN ke saath rakho. SDE 3 se expect hota hai ki celebrity problem khud bring up karo aur hybrid propose karo, inactive users handle karo, hot counters ko async aggregation se deal karo, aur cursor pagination aur eventual consistency pe baat karo.

Ek line mein yaad rakho: normal users ke liye post time pe feed precompute karo, celebrity posts read time pe pull karo, aur merge karo. Agar is video ke notes chahiye toh comment mein FEED likho, main breakdown bhej dunga. Aur comments mein batao ki kaunsa interview question aapko sabse zyada pareshan karta hai.
