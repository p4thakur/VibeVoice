Ek kaam karte hain. Maan lo aapko IRCTC ka Tatkal booking system build karne ko diya gaya hai. Aap ek design banate ho jo aapke laptop pe perfectly chalta hai. Phir subah 10 baje aate hain, 3 lakh log ek saath click karte hain, aur system 4 alag tareekon se fail hota hai. Hum wahi 4 failures ek ek karke dekhenge, aur har fix mein exact tool aur exact command dekhenge. Interview mein yahin pe aapko grill kiya jaata hai, aur har jagah main bataunga ki interviewer kya poochega.

Sabse pehle ek clarifying question, jo interview mein pehle poochna chahiye. Kya user seat khud select karta hai? Tatkal mein aam taur pe nahi. User train, date, class aur passengers deta hai, aur system berth allot karta hai. Yeh ek sawaal poora design change kar deta hai. Seat map nahi hai, toh har seat ko track karne ki zaroorat nahi. Bas ek counter chahiye: is train, is date, is class, is Tatkal quota mein kitni seats bachi hain. Matlab inventory ek counter hai, aur booking ka matlab us counter ko decrement karna. Doosra question: consistency kitni chahiye? Counter kabhi capacity se upar nahi jaana chahiye, yaani no overbooking. Lekin availability dikhane wali screen thodi stale ho sakti hai.

Ab design version 1. Client, load balancer, ek Booking Service, aur PostgreSQL. Ek inventory table, jisme train number, date, class, quota, capacity aur booked columns hain. Booking aati hai toh ek hi SQL statement chalti hai: UPDATE inventory SET booked equals booked plus 2, WHERE train aur date match karein, AND booked plus 2 capacity se kam ya barabar ho. Agar ek row update hui toh booking mil gayi, zero rows update hui toh sold out. Yeh statement atomic hai, isliye overbooking possible hi nahi. Interview mein yeh pehla check hai: pehle read karke phir write mat karo, kyunki beech mein koi aur aa jaayega. Condition ke saath ek hi statement mein update karo. Yeh design correct hai. Ab dekhte hain yeh kahan fail hota hai.

Failure number 1: ek hi row. 3 lakh users, ek hi inventory row, aur PostgreSQL ek row ke updates ko ek ke baad ek process karta hai. Isse database ka CPU low dikhta hai, lekin latency bahut high, kyunki saari transactions row lock ke wait mein khadi hain. Ab pause karo. Row ek hai, requests 3 lakh. Aap kya karoge? Sharding, read replica, ya bigger machine? Comment mein likho.

Ab answer. Sharding se kuch nahi hoga, kyunki ek row ek hi shard pe rehti hai. Read replica sirf reads ke liye hai. Bigger machine row lock ko hata nahi sakti. Real answer yeh hai: jo requests lose karne wali hain, woh database tak pahunchni hi nahi chahiye. Maan lo ek train ki ek class mein Tatkal quota 100 seats ka hai. 3 lakh mein se sirf 100 win karenge. Baaki lagbhag 3 lakh requests ko database tak le jaana waste hai.

Fix: Redis ko gate banao. Inventory counter ki ek copy Redis mein rakho. Booking request aati hai toh pehle Redis pe ek Lua script chalti hai: agar counter 2 ya usse zyada hai, toh 2 decrement karo aur success return karo, warna fail. Lua isliye, kyunki check aur decrement ek hi atomic step mein hona chahiye, aur Redis single threaded hai, toh do requests beech mein interleave nahi ho sakti. Ek Redis instance 1 lakh ke aas paas operations per second handle kar leta hai, toh yeh gate 3 lakh requests ko kuch seconds mein filter kar deta hai. Sirf jo win karte hain, unhe PostgreSQL tak jaane do.

Ab interviewer yahan zaroor poochega: Redis crash ho gaya toh counter lost ho gaya? Answer: Redis ko source of truth mat banao. Source of truth PostgreSQL hai, Redis sirf ek gate hai. Redis restart ho toh counter ko rebuild kar lo: capacity minus booked minus active holds. Aur kyunki PostgreSQL pe woh conditional update ab bhi hai, Redis galat bhi ho jaaye toh overbooking nahi hoti. Bas kuch log payment tak pahunch ke fail ho sakte hain, jo ek bad user experience hai, lekin bad data nahi.

Failure number 2: payment. Jo user win karta hai, use payment karna hai, aur usme 5 minute lag sakte hain. Counter decrement ho chuka hai, lekin booking confirm nahi hui. Agar user payment chhod de, toh woh seats wapas kaise aayengi? Yahan sabse zyada log galti karte hain: payment ke dauraan database transaction open rakhte hain. Isse har user ek connection block karta hai, connection pool exhaust ho jaata hai, aur poora system hang ho jaata hai. Hum transaction open nahi rakhte, hum ek hold banate hain.

Booking Service PostgreSQL ke bookings table mein ek row insert karta hai, status pending, expires at 10 minute baad. Saath mein SQS mein ek message daalta hai, 10 minute ke delay ke saath. SQS delay queue mein message us time tak consumer ko visible hi nahi hota. Note kar lo, SQS ka maximum delay 15 minute hai, isliye hold 10 minute ka rakho. 10 minute baad ek worker message uthata hai aur check karta hai: booking confirmed hai? Haan, toh kuch nahi karna. Nahi, toh status expired karo aur Redis counter mein 2 wapas add kar do. Yeh cron job se better kyun hai? Cron har minute chalta hai, har baar table scan karta hai, aur release mein delay aata hai. Yahan har hold apne exact expiry time pe release hota hai, event driven tareeke se.

Ab payment. Client payment gateway, jaise Razorpay ya Stripe, se baat karta hai. Card details humare server se kabhi pass nahi hoti. Payment hone ke baad gateway humare webhook ko call karta hai. Webhook ek single PostgreSQL transaction chalata hai. Pehla statement: inventory mein booked badhao, usi conditional check ke saath. Doosra statement: bookings mein status confirmed karo, WHERE id match kare AND status pending ho. Yeh last condition bahut important hai, kyunki gateway webhook retry karta hai, aur pending wali condition se doosra call kuch change nahi karta. Yahi idempotency hai. Aur agar payment 10 minute ke baad aaye, jab hold expire ho chuka tha? Webhook pehle Redis gate dobara try karta hai. Agar seats mil gayi, toh confirm. Nahi mili, toh automatic refund.

Failure number 3: jab seats sold out ho chuki hain, tab bhi 3 lakh log refresh kar rahe hain. Aur har refresh poore stack se guzarta hai. Fix: losing path ko sabse cheap rakho. Jaise hi Redis counter zero hota hai, ek sold out flag set karo, aur API Gateway ya CDN edge se hi regret ya waiting list ka response de do, bina Booking Service ya Redis lock tak pahunche. Aur retries ke liye client pe exponential backoff with jitter. Ek aur cheez: double click ya network retry se do holds nahi bane chahiye. Isliye client har booking attempt pe ek idempotency key, yaani ek UUID bhejta hai. Server Redis mein us key ko SET with NX se store karta hai. Wahi key dobara aaye, toh naya hold nahi, pehle wala result return hota hai.

Agar interviewer poochhe ki isse bhi zyada control chahiye toh? Tab booking se pehle ek virtual waiting room lagao. Users ko queue mein daalo, aur unhe position real time mein push karo. Aur pehle kuch seconds mein aane walon ko random order mein admit karo, taaki sabse fast network ya bot hi win na kare.

Failure number 4: bots. Ek script insaan se 100 guna fast hoti hai. Sirf IP pe rate limit lagana kaam nahi karta, kyunki bots IP change karte rehte hain. Isliye identity pe cost lagao. Login aur Aadhaar linked verification, aur har booking pe OTP. Bot ko har attempt pe OTP chahiye, aur humare system ko kuch compute nahi karna padta. Interview mein isko kehte hain, make abuse expensive. Saath mein API Gateway pe token bucket rate limiting, counters Redis mein, per user aur per device.

Aur do chhoti cheezein. Availability screen ke liye counter Redis se read karo aur 2 second ka cache lagao, kyunki yahan thodi stale value chalti hai. Train details, jaise route aur timing, long TTL ke saath cache karo. Aur booking ke baad jo kaam critical path pe nahi hai, jaise ticket PDF aur SMS, unhe SQS ya Kafka mein daalo. Critical path mein sirf 3 cheezein: Redis gate, hold, payment confirmation.

Ek baat clear bol dun. IRCTC ka exact internal architecture public nahi hai. Yeh woh design hai jo is tarah ke interview mein expected hota hai.

Ab level ke hisaab se expectation, meri understanding ke mutabiq. SDE 2 se expect hota hai ki aap clarifying questions poochein, inventory ko sahi model karein, conditional update se overbooking prevent karein, aur hold with expiry tak reach karein. SDE 3 se expect hota hai ki aap Redis gate aur uska failure case khud bolein, payment ke dauraan database lock rakhna kyun galat hai woh explain karein, delayed message se expiry, idempotency, aur sold out ko cheap banana khud propose karein, aur har choice ka trade-off bolein. Aur dono levels pe sabse zyada marks isse milte hain ki aap khud bolo kya fail hoga, interviewer ke poochne se pehle.

Ek line mein yaad rakho: database ko sirf winners tak pahunchne do, Redis se filter karo, hold ko delay queue se expire karo, aur losing path cheap rakho.
