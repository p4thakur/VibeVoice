Interviewer bolta hai: ek notification system design karo. Push notifications, SMS, email, sab kuch. Amazon ne iska ek version Alexa ke saath poocha, jahan device offline ho sakta hai, aur Microsoft ne Windows apps ke liye poocha. Yeh ek boring plumbing question lagta hai, aur isi wajah se candidates galat karte hain. Is video mein hum ise failure by failure build karenge, taaki aap SDE 2 ya SDE 3 ki tarah answer de sako.

Pehle basic flow. Koi service, jaise orders service, user ko batana chahti hai ki unka order out for delivery hai. Woh notification service ko call karti hai, user ID, ek type aur kuch data ke saath. Notification service decide karti hai ki kaunsa channel use karna hai, message banati hai, aur ek provider ke through bhejti hai: Android ke liye FCM, iPhone ke liye APNs, SMS ke liye Twilio jaisa provider, ya email ke liye SES. Simple. Ab ise todte hain.

Failure number 1: request ke andar provider ko call karna. Orders service notification service ko call karti hai, jo synchronously FCM ko call karke wait karti hai. Aaj FCM slow hai, 5 second le raha hai. Ab aapki orders service ke threads ek notification ka wait karte hue stuck hain, aur ek notification problem orders problem ban gayi. Notification kabhi us cheez ko block nahi karni chahiye jisne usse trigger kiya.

Fix hai queue. Notification service request accept karti hai, validate karti hai, Kafka mein likhti hai, aur turant return karti hai. Alag workers Kafka se consume karte hain aur providers se baat karte hain. Har channel ke liye alag topic rakho, push, SMS aur email, taaki slow SMS provider push notifications ko na roke. Har channel ka apna worker pool hota hai jo independently scale hota hai.

Failure number 2: sab ek hi lane mein. Subah 9 baje marketing team 2 crore users ke liye campaign trigger karti hai. Woh messages usi queue mein aate hain. Idhar ek user login OTP ka wait kar raha hai, aur OTP 2 crore promotional messages ke peeche stuck hai. User give up kar deta hai. Fix hai priority. OTP aur payment alerts jaise critical traffic ke liye alag queues, ya alag topics, rakho, aur marketing jaise bulk traffic ke liye alag. Critical queue ko dedicated workers do, taaki campaign kabhi OTP ko delay na kar sake.

Ab pause karo. Ek provider request pe timeout ho gaya. Notification gayi ya nahi? Aap kya karoge? Apna answer comment mein likho.

Yahi is question ka heart hai. Aapko pata nahi. Ho sakta hai provider ne bhej diya ho aur response lost ho gaya ho. Retry karoge toh user ko wahi notification do baar mil sakti hai. Retry nahi karoge toh user ko kuch nahi mil sakta. OTP ke liye kuch nahi milna bura hai. Payment alert ke liye do baar milna bhi annoying hai. Toh aapko retries chahiye, aur idempotency chahiye, wahi pair jo humne payments video mein dekha tha.

Retries ke liye exponential backoff with jitter use karo: 1 second baad retry, phir 2, 4, 8, thodi randomness ke saath, taaki recover hota hua provider synchronized retries ki wave se hammer na ho. Attempts ka cap rakho. Cap ke baad message ko dead letter queue mein bhejo, taaki use inspect ya replay kiya ja sake, aur kabhi chupchaap drop na ho.

Idempotency ke liye har notification ko ek unique notification ID milti hai, jo caller banata hai ya aap event se generate karte ho, jaise order ID plus event type. Bhejne se pehle worker Redis mein notification_id ke saath SET NX karta hai, ek din ke TTL ke saath. Key pehle se exist karti hai toh skip. Jahan provider support kare wahan ID provider ko bhi pass karo. Phir bhi rare duplicates honge, kyunki network ke upar exactly-once delivery possible nahi hai, toh yeh clearly bolo: system at-least-once hai deduplication ke saath, jisse duplicates bahut rare ho jaate hain.

Failure number 3: user ko spam karna. Do minute mein order status paanch baar badalta hai aur user ko paanch buzz aate hain. Ya ek bug same event ko loop mein trigger kar deta hai. Isko fix karo per user per channel rate limit se, rate limiter video wala token bucket use karke, aur collapsing se: agar same type ki kai notifications wait kar rahi hain, toh sirf latest bhejo. User preferences bhi pehle check karo. User ne marketing SMS band kiya ho sakta hai, ya raat ko quiet hours set kiye hon, aur ise ignore karne se apps uninstall hote hain, aur SMS mein legal trouble bhi. Preferences PostgreSQL mein store karo aur Redis mein cache karo.

Failure number 4: offline device. Yeh Alexa style question hai. User ka phone off hai, toh push deliver nahi ho sakta. Kya hota hai? FCM aur APNs message ko limited time ke liye hold karte hain, aur aap uspe TTL set kar sakte ho, taaki aapki cab aa rahi hai jaisi stale notification do ghante baad na dikhe. Lekin kuch notifications lost nahi honi chahiye, jaise naya message. Toh har notification ko apne database mein per-user inbox mein bhi store karo, read ya unread status ke saath. App khulne pe woh inbox pull karti hai. Push ek nudge hai, aur inbox truth hai. Channels ke beech fallback bhi rakho: agar push kuch minutes mein acknowledge nahi hua aur notification important hai, toh SMS ya email pe escalate karo.

Failure number 5: device tokens stale ho jaate hain. User app uninstall kar deta hai, lekin aapke paas uska device token abhi bhi hai. Provider error return karta hai ki token invalid hai. Us feedback ko suno, aur token delete karo, warna dead tokens pe capacity waste hoti hai, aur aap throttle ho sakte ho. Ek user ke kai devices ho sakte hain, toh per device ek token store karo.

Aur bulk ka kya? 2 crore users ke campaign ke liye ek process mein loop mat chalao. Audience ko chunks mein todo, har chunk ko ek job ki tarah Kafka pe publish karo, aur kai workers ko parallel mein process karne do, provider ki rate limit tak throttle karke. Templates aur localization ek alag template service mein rehte hain, taaki message content send time pe render ho, har caller store na kare.

Ab expectations. SDE 2 se expect hota hai ki aap Kafka se decouple karo, channels alag karo, backoff ke saath retries use karo, aur explain karo ki notification caller ko block kyun nahi karni chahiye. SDE 3 se expect hota hai ki priority lanes, idempotency aur deduplication, dead letter queue, user preferences aur rate limiting, inbox ke saath offline device, aur stale tokens khud bring up karo.

Ek line mein yaad rakho: jaldi accept karo, channel aur priority se queue karo, idempotency ke saath retry karo, aur push ko nudge samjho jabki inbox truth hai. Agar is video ke notes chahiye toh comment mein NOTIFY likho, main breakdown bhej dunga. Aur comments mein batao ki kaunsa interview question aapko sabse zyada pareshan karta hai.
