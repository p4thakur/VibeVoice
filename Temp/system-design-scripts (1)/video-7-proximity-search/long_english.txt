The interviewer says: design a system that finds all restaurants within 10 kilometers of a user. It looks like a simple database query, and this is exactly the question where candidates stumble. Microsoft asked a version of it, and even Amazon's Locker question has the same core: find the nearest store. In this video we'll solve it failure by failure, and you'll walk away with a clear answer for an SDE 2 or SDE 3 interview.

First, the naive attempt. You store latitude and longitude in a PostgreSQL table, and you write: WHERE the distance from the user is less than 10 km. To compute distance you use the Haversine formula, which involves sine and cosine functions. The problem is that the database can't use an index on a computed distance, so it calculates this for every row. With 5 million restaurants, every search is a full table scan. At a few thousand searches per second, it dies.

The second attempt: a bounding box. Compute a square around the user: latitude between lat minus delta and lat plus delta, longitude between lon minus delta and lon plus delta. Put a B-tree index on latitude and longitude. Now the query is faster. But a B-tree handles one dimension well. It can narrow down by latitude, giving you a long horizontal strip of the earth, and then it still has to filter millions of rows by longitude. Two separate one-dimensional indexes don't make a two-dimensional index.

Now pause. How would you turn a two-dimensional location into something a normal index can search? Write your idea in the comments.

The answer is to divide the world into cells, and give each location a cell ID. The most popular way is geohash. Geohash splits the map into a grid, then splits each cell again and again, and encodes the result as a short string. The magic property: nearby places share a common prefix. A longer prefix means a smaller cell. A 5-character geohash is a cell of roughly 5 kilometers by 5 kilometers, and a 4-character one is roughly 39 by 20 kilometers. Now a location search becomes a string prefix search, and a normal index can do that quickly.

So the plan: store each restaurant with its geohash. For a 10 km search, compute the user's cell, fetch restaurants in that cell, and then filter by exact distance. But here comes failure number 2: the boundary problem. A user may stand at the edge of a cell. A restaurant just 200 meters away can be in the neighboring cell, with a completely different prefix. If you search only the user's cell, you miss it. So you always search the user's cell plus its 8 neighbors, which is 9 cells. Then you compute the exact distance for the candidates, remove those beyond 10 km, sort by distance, and return. Remember this sentence: the grid finds candidates, the exact distance gives the answer.

Failure number 3: choosing the cell size. If the cells are too big, every search pulls thousands of candidates and the exact distance filter becomes the cost. If too small, a 10 km radius needs dozens of cells. Pick the precision from the radius, so that a search touches a small, fixed number of cells. This is a good thing to say out loud.

Failure number 4: uneven density. Mumbai has thousands of restaurants in one cell, while a desert has none. A uniform grid treats them the same. This is where a quadtree helps: it keeps splitting a cell only when it holds too many points, so dense areas get fine cells and sparse areas get big ones. Uber's H3 and Google's S2 are similar ideas with better geometry: H3 uses hexagons so all neighbors are the same distance away. You don't need to implement them, but naming them is a strong signal.

Now, which tool do you actually use? There are three good answers. For static places like restaurants, PostGIS in PostgreSQL has a spatial index, a GiST index, and queries like ST_DWithin run fast. Elasticsearch has a geo_distance query too, and it's useful when you also need text search and filters like cuisine or rating, which is exactly what a food app needs. And for fast-moving objects, like delivery partners or cabs, use Redis GEO. Redis stores locations in a sorted set, using a geohash as the score. GEOADD adds a location and GEOSEARCH finds everything within a radius. It's in memory, so it handles constant location updates.

That distinction is the real insight: static data versus moving data. Restaurants rarely change, so index them in PostGIS or Elasticsearch and cache popular cells. Drivers move every few seconds, so keep their latest location in Redis, and put a TTL so a driver who goes offline disappears automatically. Don't write every GPS ping to your main database.

Failure number 5: scale. One Redis or one database can't hold the whole world. Shard by geography. Use the geohash prefix or the city as the shard key, so one search touches one shard, or a few at most. But watch out for hotspots, because Mumbai during dinner time is far hotter than a small town. Handle it by splitting hot regions into smaller cells, or by giving big cities their own shards. Read replicas also help, since reads dominate.

If the interviewer then asks about the Amazon Locker style question, find the nearest store with available slots, the answer is the same grid, with one extra step: the candidates are filtered by availability before sorting by distance.

Now, expectations. At SDE 2, you should reject the full table scan, explain geohash or a similar grid, and handle the neighbor cells. At SDE 3, you should bring up the boundary problem and uneven density yourself, separate static from moving data, choose tools like PostGIS, Elasticsearch and Redis GEO, and explain how you shard by geography.
