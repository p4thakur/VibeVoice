Here's a question that comes up in almost every fintech interview loop. A user's payment times out, but on the backend it actually succeeded. The user retries. How do you stop a double debit? In this video we'll solve it through 4 failures, and with every fix you'll see the exact table, the exact constraint and the exact API call. And note one thing right now: just saying "use an idempotency key" is only half the answer. The full answer comes by the end.

First, the simple flow. The client sends a request to the Payment Service. The Payment Service calls a payment gateway, which we'll call the PSP, like Razorpay or Stripe. The PSP debits the customer, a response comes back, and we write status success in our database. On your laptop this works perfectly. Now let's see where it breaks in production.

Failure number 1: the client retry. The network times out, the client gets no response, so it sends the request again. The server thinks it's a new payment, and a second debit happens. The fix is an idempotency key. For every logical payment, the client generates a UUID, for example the moment the Pay button is clicked, and sends it in a header. A retry carries the same key. Now here's the most common mistake. Candidates store the key in Redis with SET and NX and think they're done. But Redis restarts, or the key expires, or the process crashes after the charge and before the Redis write, and a duplicate walks straight in. The real guard is a UNIQUE constraint in the database.

Here's the design. An idempotency table in PostgreSQL with columns for the key, a hash of the request, a status and the stored response, with a UNIQUE constraint on the key. The moment a payment arrives, step one is to INSERT into this table with status IN PROGRESS. A second request with the same key violates the constraint and fails, and we know it's a duplicate. And this insert must happen in the same transaction as the payment row. If you write the key in one place and the payment row in another, a crash in between breaks idempotency.

On a retry there are three cases. The key is IN PROGRESS: the first request is still running, so return 409 conflict, or wait for the result. The key is COMPLETED: return the stored response, with no new charge at all. And the key is the same but the request body is different, say the amount changed: that's a client bug, so reject it. That's why we store the hash of the request.

Failure number 2: this is the real interview question. The Payment Service called the PSP, the PSP debited the money, and right then the Payment Service crashed, or the PSP's response timed out. In our database the status says PROCESSING. We don't know whether the money moved. This is called the unknown state, and the whole design is built around it. Now pause. In this state, what would you do? Mark it failed and let the user retry, or charge again? Write it in the comments.

Both are wrong. If you mark it failed and the money actually moved, the user never finds out, and support tickets flood in. If you charge again, that's a double debit. The right way is to model the payment as a state machine: CREATED, PROCESSING, SUCCESS, FAILED, and an explicit state called UNKNOWN. On a timeout, set the status to UNKNOWN. Then a background worker calls the PSP's status check API and marks SUCCESS or FAILED based on the result. And remember one rule: before you call the PSP, commit the payment row with status PROCESSING to the database. Then make the call. That way, if you crash, you still have a record you can verify later.

And if you really must retry, forward the same idempotency key to the PSP. PSPs have their own idempotency mechanism; Stripe has an Idempotency-Key header. So idempotency has to be end to end: our key mapped to the PSP's key. Otherwise the guarantee stops at our own system, and money can still move twice.

Failure number 3: webhooks. The PSP sends the final result through a webhook. Webhooks get retried, they arrive duplicated, and sometimes out of order. A FAILED event can arrive after SUCCESS. The fix has two parts. First, store every webhook's event id in a table with a UNIQUE constraint, and if the same event comes again, ignore it. Second, the status should only move forward. Write the update like this: UPDATE payments SET status equals SUCCESS WHERE the id matches AND status is PROCESSING or UNKNOWN. If the payment is already SUCCESS, zero rows are updated, and a late FAILED event affects nothing. Also, the webhook handler should return 200 quickly and push the heavy work to a queue, otherwise the PSP will think it failed and retry.

Failure number 4: you did everything right, and some payments still mismatch. SUCCESS in the PSP's records, FAILED in ours. That's why you need reconciliation. Every day, match the PSP's settlement file against your own records, and run an alert or an auto-fix for mismatches. At staff level, mentioning reconciliation is mandatory, because it shows you've run a real money system. And what about balances? Never write UPDATE balance SET amount equals amount minus 100. Build a double-entry ledger: every transaction has two rows, a debit and a credit, in a single database transaction, and the two sum to zero. That way every rupee is traceable and auditable.

Now the interviewer's follow-ups. Who generates the idempotency key, the client or the server? The client, because on a retry the server has no way of knowing it's the same operation. How long do you store keys? Longer than the retry window, say 24 hours, not forever, or the table gets huge. And if the operation failed before the charge, what happens to the key? Mark that row FAILED and decide whether the client uses a new key or the retry is allowed. That's a design decision, and you should say it out loud in the interview.

Now the expectation at each level, based on my understanding. At SDE 2 you're expected to reach the idempotency key, a database UNIQUE constraint and webhook handling. At SDE 3 you're expected to handle the unknown state with a state machine, persist the record before the PSP call, keep idempotency end to end through to the PSP, and bring up reconciliation and the double-entry ledger yourself, before the interviewer asks.

In one line: lock the key with a UNIQUE constraint in the database, write the record before the call, give the unknown state a name, and reconcile daily.
