Everything goes smoothly in an interview, right up until you say: I'll use a Redis distributed lock here. Then the interviewer asks one question: what if the lock's TTL expires while the old client is still working? Or, more directly: is a Redis lock even safe? This is exactly where SDE 2 and SDE 3 candidates separate. In this video we'll solve the question as a story, and by the end you'll have an answer that genuinely impresses the interviewer.

First, a simple Redis lock. The client runs one command: SET the lock key to a unique value, with NX and PX 30000. NX means set only if the key doesn't already exist. PX 30000 means the key expires by itself after 30 seconds. The client that successfully runs the SET has taken the lock. When the work is done, it releases the lock, but there's one important detail: when releasing, first check that the lock's value is yours, and only then delete it. That check and delete must be atomic in a Lua script. Otherwise one client can delete another client's lock. That's the first mistake candidates make.

Now, why a TTL? Because if a client crashes and never releases the lock, that lock would be stuck forever. The TTL saves you from that. But this is exactly where the real problem begins.

Failure number 1: the lock expires while the client is still alive. Client A takes the lock, with a 30-second TTL. Then A hits a long GC pause, or a network delay, or the process freezes for a while. 30 seconds pass, and the lock expires. Client B takes the lock and writes to the database. Now A resumes, still believes it holds the lock, and writes too. Two clients modified the protected resource together, and the data is corrupted. Martin Kleppmann explained exactly this scenario in 2016, and it doesn't happen because of a bug. It happens just because of timing.

Now pause. What would you do to fix this problem? Increase the TTL, or something else? Write it in the comments.

Increasing the TTL only postpones the problem, it doesn't remove it. A pause can be arbitrarily long. The right fix is a fencing token. The idea is this: the lock service hands out a number with every lock, and that number always increases. So A got token 33, and later B got token 34. Now when a client writes to storage, it sends its token along. The storage's job is to reject any write whose token is smaller than the largest token it has seen. So B wrote with token 34. When A resumes and sends its write with token 33, the storage sees that 33 is smaller than 34, and rejects it. Now the lock is truly safe, because the safety lives not in the lock service but on the resource.

Now the question: does Redis give you a fencing token? The direct answer: no. Redis's SET NX lock doesn't give you any increasing token by itself. You can build a separate counter with INCR, but that isn't safe during failover either. ZooKeeper and etcd are different here. In ZooKeeper, a lock is a znode, and its version number or transaction id, called the zxid, naturally keeps increasing, so it can serve as a fencing token. In etcd, the revision number does the same job. That's why, when correctness is truly critical, consensus systems like ZooKeeper or etcd are preferred.

Failure number 2: Redis failover. Say you use one Redis master and one replica. A client takes the lock on the master. Replication is asynchronous, so the lock hasn't reached the replica yet, and the master crashes. The replica gets promoted, and it doesn't have that lock at all. Now client B easily takes the same lock, and both A and B hold it.

Redlock was built for exactly this problem. The idea: 5 independent Redis masters, with no replication between them. The client tries to take the lock on all 5, and if it gets it on at least 3, which is a majority, and the total time taken is less than the TTL, the lock is valid. Even if one master fails, the lock survives.

But Kleppmann raised two questions about Redlock. First: Redlock depends on timing assumptions, like clocks running correctly and pauses being bounded. In distributed systems, those assumptions don't hold. Second, and more fundamental: Redlock gives no fencing token, so the GC pause problem stays. Redis's creator, antirez, replied that the pause problem isn't just Redlock's, it affects every lock service, and that if you need fencing you can layer it on separately. Both sides have valid points, and knowing this debate in an interview is a strong signal.

Now Kleppmann's most useful point, which you should say in the interview: a lock is taken for one of two reasons. The first is efficiency: so the work isn't done twice, like an expensive report not being generated twice. Here, if the lock occasionally fails, you only pay a small cost, so a simple single Redis lock is perfectly fine, and you don't need Redlock's complexity. The second is correctness: if two clients work together, the data gets corrupted, like money or a seat. Here, don't trust the lock alone.

And now the real interview answer, which connects to the Tatkal video. For correctness, the resource itself must guard against it, on top of the lock. We saw this in Tatkal: the Redis lock or counter is only for user experience, so that fewer people reach payment just to fail. But the real guard is the conditional update in PostgreSQL: UPDATE seats SET status equals booked, version equals version plus 1 WHERE the id matches AND status is available AND the version matches. That version column works like a fencing token. A stale client that resumes late has an old version, and its update affects zero rows and fails. So even if the Redis lock goes down, expires or is duplicated, the data is never corrupted. This is called defense in depth.

Now the expectation at each level, based on my understanding. At SDE 2 you're expected to build a lock with SET NX PX, and release it with an owner check. At SDE 3 you're expected to bring up the GC pause and TTL expiry scenario yourself, explain the fencing token, and say that for correctness the resource itself must be guarded, like with a database conditional update or a version check. Knowing the Redlock debate is extra credit.

In one line: a Redis lock is fine for efficiency, but for correctness you need a fencing token or a database version check.
