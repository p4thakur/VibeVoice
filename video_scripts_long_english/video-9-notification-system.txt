The interviewer says: design a notification system. Push notifications, SMS, email, all of it. Amazon asked a version of this with Alexa, where the device may be offline, and Microsoft asked it for Windows apps. It sounds like a boring plumbing question, and that's exactly why candidates get it wrong. In this video we'll build it failure by failure, so you can answer like an SDE 2 or SDE 3.

First, the basic flow. Some service, say the orders service, wants to tell a user that their order is out for delivery. It calls the notification service with a user ID, a type and some data. The notification service decides which channel to use, builds the message, and sends it through a provider: FCM for Android, APNs for iPhone, an SMS provider like Twilio, or an email provider like SES. Simple. Now let's break it.

Failure number 1: calling the provider inside the request. The orders service calls the notification service, which synchronously calls FCM and waits. FCM is slow today, taking 5 seconds. Now your orders service threads are stuck waiting for a notification, and a notification problem has become an orders problem. A notification must never block the thing that triggered it.

The fix is a queue. The notification service accepts the request, validates it, writes it to Kafka, and returns immediately. Separate workers consume from Kafka and talk to providers. Use separate topics per channel, push, SMS and email, so a slow SMS provider doesn't hold back push notifications. Each channel has its own worker pool that scales independently.

Failure number 2: everything in the same lane. At 9 AM, the marketing team triggers a campaign for 20 million users. Those messages enter the same queue. Meanwhile, a user is waiting for a login OTP, and the OTP is stuck behind 20 million promotional messages. The user gives up. The fix is priority. Use separate queues, or separate topics, for critical traffic like OTPs and payment alerts, and for bulk traffic like marketing. Give the critical queue dedicated workers, so a campaign can never delay an OTP.

Now pause. A provider times out on a request. Did the notification get sent or not? What do you do? Write your answer in the comments.

That's the heart of this question. You don't know. The provider may have sent it and the response got lost. If you retry, the user may get the same notification twice. If you don't retry, the user may get nothing. For an OTP, nothing is bad. For a payment alert, two is also annoying. So you need retries, and you need idempotency, the same pair we saw in the payments video.

For retries, use exponential backoff with jitter, retry after 1 second, then 2, 4, 8, with some randomness, so a recovering provider isn't hammered by a synchronized wave of retries. Cap the number of attempts. After the cap, send the message to a dead letter queue, so it can be inspected or replayed, and never silently dropped.

For idempotency, every notification gets a unique notification ID, created by the caller or generated by you from the event, like order ID plus event type. Before sending, the worker does SET notification_id with NX in Redis, with a TTL of a day. If the key already exists, skip. Also pass the ID to the provider where they support it. You'll still have rare duplicates, because exactly-once delivery is not possible across a network, so say that clearly: the system is at-least-once with deduplication, which makes duplicates very rare.

Failure number 3: spamming the user. An order status changes five times in two minutes and the user gets five buzzes. Or a bug triggers the same event in a loop. Fix this with a rate limit per user per channel, using the token bucket from the rate limiter video, and with collapsing: if several notifications of the same type are waiting, send only the latest. Also check user preferences first. The user may have turned off marketing SMS, or set quiet hours at night, and ignoring that is how apps get uninstalled and, for SMS, how you get into legal trouble. Store preferences in PostgreSQL and cache them in Redis.

Failure number 4: the offline device. This is the Alexa style question. The user's phone is off, so the push can't be delivered. What happens? FCM and APNs hold the message for a limited time, and you can set a TTL on it, so a stale notification like your cab is arriving doesn't show up two hours later. But some notifications must not be lost, like a new message. So also store every notification in a per-user inbox in your own database, with a read or unread status. When the app opens, it pulls the inbox. The push is a nudge, and the inbox is the truth. Also, fall back across channels: if the push isn't acknowledged in a few minutes and the notification is important, escalate to SMS or email.

Failure number 5: device tokens go stale. A user uninstalls the app, but you still hold their device token. The provider returns an error saying the token is invalid. Listen to that feedback, and delete the token, otherwise you waste capacity on dead tokens, and may get throttled. A user may have several devices, so store a token per device.

And what about bulk? For a campaign to 20 million users, don't loop in one process. Split the audience into chunks, publish each chunk as a job to Kafka, and let many workers process them in parallel, throttled to the provider's rate limit. Templates and localization live in a separate template service, so the message content is rendered at send time, not stored by every caller.

Now the expectations. At SDE 2, you should decouple with Kafka, separate channels, use retries with backoff, and explain why a notification must not block the caller. At SDE 3, you should bring up priority lanes, idempotency and deduplication, a dead letter queue, user preferences and rate limiting, the offline device with an inbox, and stale tokens.

In one line to remember: accept fast, queue by channel and priority, retry with idempotency, and treat the push as a nudge while the inbox is the truth.
