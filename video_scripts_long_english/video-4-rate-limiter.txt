The rate limiter is one of the most common questions in system design interviews. In almost every API-related design round, it shows up either as a standalone question, or as a component you have to add yourself. Most candidates say "token bucket" and stop. In this video we'll build a rate limiter that holds up even against Tatkal's 300,000 users, and we'll go through 4 failures to see where every wrong design breaks. At every step you'll also see the exact algorithm and the exact Redis command.

First, the clarifying questions you should ask at the start of the interview. What do you limit on: user id, IP, or API key? Is it a hard limit, or is some burst allowed? Is the limit on one service, or on the whole system? And when the limit is crossed, what should happen: reject the request, or queue it? We'll assume: a per-user and per-IP limit, a little burst allowed, and rejecting the request.

Failure number 1: a counter on every server. The first design that comes to mind: each app server keeps a counter in its own memory. But if you have 10 servers and the load balancer spreads the requests, every user effectively gets 10 times the limit. And when a server restarts, its counter resets. The limit isn't really enforced. So the counters have to live in a shared store, and this is where Redis comes in: fast, in memory, and one instance handles around 100,000 operations per second.

Failure number 2: the race condition. Now the counters are in Redis. But the candidate writes this: GET the count, and if it's below the limit, SET the count plus 1. Those are two separate commands. Two requests arrive together, both see the count as 99, both allow it, and the limit of 100 becomes 101. In the same way, with 300,000 requests the limit would be crossed by a huge margin. The fix: the check and the update must be one atomic step. For a simple fixed window counter, the INCR command is atomic, and you add EXPIRE alongside it. For more complex algorithms, use a Lua script, because Redis runs a Lua script without interruption.

Failure number 3: the fixed window boundary burst. A fixed window counter is simple: one counter per minute, limit 100. But a user sends 100 requests at 12:00:59, and another 100 at 12:01:00. That's 200 requests in two seconds, and no window's rule was broken. At the boundary you get double the burst. Now pause. Which algorithm would you choose to fix this problem? Write it in the comments.

Now the comparison of algorithms, which is the core of the interview. Sliding window log: store every request's timestamp in a Redis sorted set, and remove timestamps that are outside the window. The accuracy is perfect, but memory per user grows with the number of requests, which is expensive at scale. Sliding window counter: keep two fixed window counters, the previous window and the current one. The estimate is the previous window's count, multiplied by the remaining fraction of that window, plus the current window's count. Memory is just 2 counters per user, and the accuracy is quite good. Token bucket: each user has a bucket with a capacity of tokens, and tokens refill at a fixed rate. Every request consumes one token. If the bucket is empty, reject. Bursts are allowed up to the capacity, and the average rate stays smooth. That's why most public APIs use token bucket. Leaky bucket smooths the output to a constant rate, which is better for network traffic shaping and used less for APIs.

My recommendation: for a user-facing API like Tatkal, token bucket, because a little burst is fine and memory is O(1). For high-volume internal APIs, the sliding window counter.

Now the implementation. A token bucket is stored in Redis as a hash with two fields: tokens and last refill time. A Lua script runs. First it reads the bucket's state. Then it computes the difference between the current time and the last refill time, and adds as many tokens as should have refilled in between, never above the capacity. Then if tokens are 1 or more, it deducts one token and returns allow; otherwise it returns reject. Then it writes the new state back to the hash, and sets an EXPIRE on the key, so the keys of inactive users are deleted automatically. This whole thing is one atomic step, so there's no race condition.

For a rejected request, return 429 Too Many Requests, along with a Retry-After header, so the client knows when to try again. You can also send headers like X-RateLimit-Remaining. And on the client side, use exponential backoff with jitter, so rate-limited clients don't retry together and create a storm.

Failure number 4: Redis itself goes down. Now the question is: if the rate limiter fails, do you block all requests, or allow all of them? This is a design decision, and you should say it out loud in the interview. For a normal API, fail open: if the limiter is down, allow the requests, because availability matters more. But for abuse-sensitive endpoints like login, OTP or payment, fail closed, or apply a strict local limit. And Redis latency is a cost too, because every request makes one network hop. You can keep a local in-memory limiter as a first line of defense, and use Redis for the global limit.

One more follow-up: multiple regions. If users are in 2 regions, enforcing a global limit is hard, because syncing between regions has latency. The common approach is to give each region a share of the limit, say 50 and 50 out of 100, and stay a little approximate. Perfect global accuracy is usually not needed.

And the idea of layers: the limit isn't applied in just one place. Per user, per IP and global at the system level, all three are separate. The global limit still works when an attacker uses a lot of IPs.

Now the expectation at each level, based on my understanding. At SDE 2 you're expected to explain token bucket or a sliding window, and to keep the shared counter in Redis. At SDE 3 you're expected to solve the race condition with Lua, state the trade-offs between algorithms, explain the fail open versus fail closed decision, and propose a multi-region plan yourself.

In one line: keep the shared counter in Redis, do the check and the update in one atomic Lua script, use token bucket for bursts, and decide in advance what happens when Redis goes down.
